# Granular Authorization

Implementation rules for the granular authorization model accepted in [ADR-0030](../../../docs/adr/0030-granular-authorization.md). Domain vocabulary is in the [OntOS context](../../../docs/contexts/ontos/CONTEXT.md#granular-authorization).

This is the only authorization model. It replaced the explicit Action-grant model of [ADR-0019](../../../docs/adr/0019-explicit-action-authorization.md) directly: there is no legacy relation set to fall back to, no dual read or write, no feature flag for the earlier path, and no migration or import step. Every protected entrypoint is gated by the declaration it carries, and one decision function answers Actions, reads, fields, exports, pages, navigation, search and access administration.

## The one gate

Every protected entrypoint calls the Core enforcement seam (`packages/core-runtime/src/access/enforcement/`). `AccessDecisionService` in `access/enforcement/contract.ts` is the only authorization surface:

| Method                    | Question                                                                                            |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| `decide`                  | May this actor run this one entrypoint now?                                                         |
| `decideMany`              | The same question for several entrypoints in one engine call (navigation, search providers).        |
| `list`                    | Which rows of a list, search, history or report may this actor read? Returns the owner's predicate. |
| `selectableLegalEntities` | Which companies may this actor select (`access_legal_entity#select`)?                               |

`decide` takes the trusted `scope` (acting principal, tenant and optional legal entity), the entrypoint's decoded `carrier`, its declared `legalEntityScope`, an optional record `target`, an optional `amount`, an optional `parentRead`, a `mode` and a Core-minted `now`. It returns the engine's `AccessDecision`.

| Outcome          | Meaning                                                                                             |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| `ALLOWED`        | Run the entrypoint.                                                                                 |
| `DENIED`         | Refuse with `403`.                                                                                  |
| `NEEDS_APPROVAL` | Refuse with `403` `action_approval_required`: the actor may propose but not run.                    |
| `UNAVAILABLE`    | Retryable `503`: an engine, transport, deadline or consistency-fence failure that cannot be proven. |

The gate fails closed. A missing or invalid caveat context, and a caveat that leaves the permissionship indeterminate, is `DENIED` and logged as a defect, because retrying cannot repair it.

Six seam refusals are decided before the engine is read: `deny.declaration_missing` (a protected descriptor reached the gate without a carrier), `deny.principal_kind_forbidden` (the principal has no verified human kind), `deny.agent_forbidden` (an agent reached a capability no agent may use, or a workload reached an `admin` declaration, O81), `deny.workload_forbidden` (a trusted workload reached a declaration carrier), `deny.workload_unbound` (a workload reached a workload carrier with no active binding for one of its declared keys, or with an owner-declared company that does not name the company the request selects, D6) and `deny.workload_only` (a human or agent reached a workload carrier). One seam admittance, `allow.workload`, admits a registered workload on a carrier that declares `accessWorkload`; it is the owner's classification, not a v2 grant, so the engine is never asked and no decision is logged.

`list` is how a row-scoped read enforces O25. The engine returns a `ListAccessPredicate`; the runtime passes it as the optional fourth parameter of the read's `ReadServiceFactory` and on the handler context as `listAccess`, and the owner applies it inside its own query. It is present exactly for a row-scoped read decided by the gate; it is absent for a detail or scope-wide read, and an owner factory that both an Action and a read build simply declares no fourth parameter. An empty `groups` list means every row of the scope is visible, and the gate never answers an allowed list without a predicate. An owner list query never fetches rows and filters them afterwards, and never sorts or filters by a field the actor cannot read.

## Entrypoint classification

Every descriptor declares exactly one `authorization` classification:

| Kind                      | Access metadata it carries                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `public`                  | None. An intentional public result.                                                                                        |
| `authenticated_principal` | None. Any authenticated principal in a resolved scope.                                                                     |
| `protected`               | `accessDeclaration`, `accessWorkload` or `accessActor`; human, direct-workload and delegated-module paths remain distinct. |
| `owner_local_background`  | None. Owner-local background work.                                                                                         |
| `capability_issuance`     | `credential: 'api_key' \| 'session'`. A credential issuer.                                                                 |

`protected` replaced both earlier protected kinds. An Action is always `protected`; a worker is always `owner_local_background`; pages, components, APIs, search providers, reports and governed reads are `public`, `authenticated_principal` or `protected`; an API may also be `capability_issuance`.

A protected entrypoint without a carrier is a definition-time error (`missingAccessCarrierIssue` in `authorization/access-declaration.ts`), never a reported gap. Unprotected entrypoints carry no access metadata and never call the gate. Route metadata is wrapped in `defineRouteMeta` (`modules/route-meta.ts`) so a page classification cannot drift from its declaration.

## Access carriers on a descriptor

| Field                    | Entrypoints                                         | Meaning                                                                                                                                                                                                                                                                            |
| ------------------------ | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accessDeclaration`      | Actions, governed reads, pages, shell contributions | The entrypoint's own human capability. Optional when `accessWorkload` or `accessActor` stands alone.                                                                                                                                                                               |
| `accessWorkload`         | Actions, governed reads                             | `{ reason, workloads }`: only the registered machine workloads named by `workloads` may run this entrypoint. Never in the configurable catalog, never granted to a human or an agent.                                                                                              |
| `accessActor`            | Actions, governed reads                             | `{ reason, callers, subject, subjectWorkloads? }`: only a verified calling module named by `callers` may act for the subject. `rights` checks the human subject's declaration; `identity` admits its verified identity. `workload` admits only an actively bound workload subject. |
| `accessFieldGroups`      | Actions (write), governed reads (read)              | Sensitive field groups. Requires the descriptor's own `accessDeclaration`; its parent read is that declaration (one record when record-scoped, scope-wide otherwise, O74).                                                                                                         |
| `accessTarget`           | Actions, governed reads                             | `(payload \| input, scope) => { moduleKey, recordKey }`: the one record a record-scoped declaration acts on. Only on a declaration with selectors.                                                                                                                                 |
| `accessAmount`           | Actions                                             | `(payload, scope) => AccessAmount`: the governed money value, for an owner-derived total only. When declared, the declaration's `amountInput` must name a `derived.*` path.                                                                                                        |
| `accessOwnerFacts`       | Actions, governed reads                             | `(payload \| input, scope) => Record<string, string>`: owner-local facts for the owner overlay (O70). They never reach the engine and never grant.                                                                                                                                 |
| `accessReducesAuthority` | Actions                                             | `(payload) => boolean`: when true the runner skips the grant decision because the Action only reduces authority (O35). It still requires an authenticated principal in a resolved scope and records the act.                                                                       |

`accessTarget` is required by the runner when the declaration names record selectors; a missing target is `deny.target_required`. A scope-wide declaration (`selectors: []`) that declares `accessTarget` is a definition-time error. A scalar `amountInput` is read from the decoded payload directly. `accessAmount` is only for an owner-derived total: when an Action declares it, the declaration's `amountInput` must name a `derived.*` path, never a client-supplied amount (O18). `accessTarget` and `accessOwnerFacts` are different channels: targets become engine selectors, owner facts go only to the owner overlay.

A module-only workload purpose declares `accessActor.subject = workload` and a nonempty `subjectWorkloads`.
It declares no `accessDeclaration`, `accessWorkload` or `accessFieldGroups`, so it creates no human catalog
capability and no cell in the initial full-access role. The subject workload key belongs to the calling
flow's module namespace, not the receiving owner's namespace; `callers` contains the topology app IDs.
Core requires the gateway-verified `act` identity and an active tenant/principal workload binding. Humans,
agents, direct calls without `act`, unlisted callers, unbound workloads and approval/proposal attempts
cannot execute this purpose. A failed registry read remains unavailable. An allowed list gets an explicit
all-in-scope predicate; the owner still enforces its purpose and trusted company scope.

On the existing `rights` and `identity` modes, `subjectWorkloads` remains an additional workload path,
not an exclusivity marker. Its presence does not remove the human declaration or change sensitive field
projection. Removing a purpose from human access therefore requires the explicit `workload` mode, not
filtering keys out of an otherwise complete bootstrap role.

## The declaration

`packages/core-runtime/src/authorization/access-declaration.ts` owns the exact schema, validation and the dangerous-verb, terminal-verb and sensitive-field-class constants. Do not restate its rules in module code.

| Field         | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `key`         | Lowercase `<moduleId>.<resource>.<verb>[.<qualifier>]`, starting with the owning module's full dotted `moduleId` and unique within it: `party.registry.party.merge` is module `party.registry`, resource `party`, verb `merge`. The module ID is matched as one whole prefix, so the verb rules only look at the segments after `<moduleId>.<resource>`. It is the permission's identity; changing it is a rename (see lineage).                                                                                                                                                   |
| `kind`        | `action`, `read`, `field_read`, `field_write`, `export` or `admin`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `risk`        | `routine`, `sensitive` or `critical` (see below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `placement`   | Suggested editor `group` and `level` (`basic`, `extended`, `manage`). A suggestion for the Role editor and templates, never a grant.                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `selectors`   | Record scopes the entrypoint can filter by: `all`, `assigned`, `entrusted`, `team`. Use `[]` when it is not record-scoped.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `modes`       | `run`, `propose`, `approve`. Reads and field reads use exactly `['run']`. A sensitive or critical Action must include `propose`; `approve` is optional, and without it only a granted person runs the Action directly. `approve` requires `propose`. An identity-bound Action, which the original actor must personally run, uses `['run', 'propose']` and never `approve`; an Action that is itself an approval decision declares `['run']` or `['run', 'propose']` with the risk of its own effect. An `ephemeral` Action and a kind `admin` Action may declare `['run']` alone. |
| `ephemeral`   | `true` only for a short-lived proof whose validity is seconds to minutes and that cannot wait for a person, such as a 30-second commitment confirmation. It must then be run-only, and agents never run it when its risk is sensitive or critical.                                                                                                                                                                                                                                                                                                                                 |
| `amountInput` | Actions only: the path of the money input that amount limits apply to. A composite money value must be named through a server-derived `derived.*` total (O18).                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `fieldClass`  | Required for `field_read` and `field_write`, forbidden otherwise. Take the class from the module's own meaning. `personal_data`, `bank_details`, `salaries`, `margins`, `purchase_prices`, `credit_limits`, `financial_amounts`, `tax_identifiers` and `authority_metadata` carry a `sensitive` floor; any other lowercase class, such as `commercial_activity`, is allowed and listed for review in the catalog report.                                                                                                                                                           |
| `lineage`     | `renamedFrom` keeps identity and access across a rename; `splitFrom` registers a split whose halves nobody inherits automatically. Lineage stays inside the owning module and never forms a cycle.                                                                                                                                                                                                                                                                                                                                                                                 |

### Choose the risk tier

- `critical`: money movement, irreversible or legal effect, destructive operations, and authority or admin changes.
- `sensitive`: personal data, financial visibility, exports, bulk changes and external communication.
- `routine`: everything else.

Validation enforces the floor:

- `export` and `admin` are at least `sensitive`.
- A `fieldClass` with a sensitive floor is at least `sensitive`.
- A key containing a dangerous verb is never `routine`, whatever its spelling, case or separators: anonymize, approve, cancel, close-period, credit-note, delete, erase, export, grant, impersonate, merge, pay, payout, publish, purge, refund, remove, retire, revoke, transfer, void, write-off.
- A routine key containing a terminal verb (`archive`, `close`, `deactivate`) is surfaced for review as the catalog finding `routine_terminal_verb`. The tier should be at least `sensitive`, and `critical` when the change has a legal or money effect or cannot be undone.

When in doubt, choose the higher tier. Risk only decides warnings, Adoption and agent limits, never a grant.

### Agent policy

Agent behaviour is derived from kind and risk, never declared per entrypoint. A routine declaration is `run`; a sensitive or critical Action is `propose_only`; a sensitive or critical read, field access or export is `never`, because a read cannot be proposed; a kind `admin` declaration is `never`. A dual carrier follows its declaration, because the declaration is the human and agent capability of the descriptor.

## Field groups

A read or Action may carry `accessFieldGroups: readonly AccessFieldGroupInput[]` beside its `accessDeclaration`. Each group is its own declaration with `kind: 'field_read'` on a read or `'field_write'` on an Action, a required `fieldClass` (O19 floors apply), `fields: readonly string[]` naming the result or payload paths it governs, its own key in the same module prefix, `risk`, `placement`, `selectors: []` and modes (`field_read` is run-only; `field_write` is run-only or `['run', 'propose', 'approve']`). A group is never record-scoped and never the key of its parent declaration. A descriptor with field groups must also declare its own `accessDeclaration`, because field access needs access to the read it belongs to. The catalog lists groups as their own entries.

Field access rides the parent read of the declaration it belongs to (D14, O74), and the shape of that parent read follows the entrypoint:

- **Record-scoped entrypoint** (the declaration names record selectors): the read or Action declares `accessTarget`, and every group is decided with that one record and that record's own read.
- **Scope-wide entrypoint** (`selectors: []`): no `accessTarget` is needed, and declaring one is a definition-time error because a scope-wide capability acts on no single record. The parent read is the containing declaration's own capability, decided scope-wide in the same scope and in the same engine snapshot (`CheckBulk`) as the group. This is how a staff module governs, for example, purchase costs separately from selling prices without inventing a record scope.
- **Row-scoped read** (`list`, `report`, `search`): the groups are decided scope-wide exactly as declared, and the read's own row predicate bounds the rows they apply to (O25).

The runtime channels are part of the contract, not of the declaration. A result field the caller may not read is omitted from the projection (O17: the canonical payload is decoded, validated and hashed whole server-side and only then redacted), and a payload that writes a `field_write` field the caller may not write is refused with 403 before the handler runs. Only a field the payload really writes is governed, so an Action that governs one sensitive field keeps every other field writable for the same caller; a `field_write` group whose sensitive field may only be proposed answers `action_approval_required` instead. An unreadable field decision is a retryable 503, never a silent projection and never a silent allow.

## Workload-only and dual carriers

A carrier that declares `accessWorkload` is for trusted machine workloads only (O29/O59/O73). A human or agent reaching it is refused with `deny.workload_only`; a workload reaching a declaration-only carrier is refused with `deny.workload_forbidden`. An Action or a governed read may declare both carriers (dual): the workload path admits workloads and never humans, and the declaration path admits humans and agents and never workloads. `accessWorkload` never stands beside `accessFieldGroups`, and never appears on a page, a shell carrier, or an `authenticated_principal` or `public` read.

A workload is admitted by registered identity, never by its principal kind (O73). `accessWorkload` names the workload keys it admits (`{ reason, workloads: ['commerce.storefront-client'] }`), each a `<module>.<workload-name>` key in the carrier module's own namespace. Core keeps the bindings in `core.access_workload_bindings` (tenant, principal, workload key, status, incarnation), written only by the install/bootstrap path — the stage accounts file's per-tenant `workloads` list, the local development seed, and later a Core admin Action. The gate reads the acting workload's active bindings before it admits it: a `service`, `integration` or `system` principal with no active binding for one of the carrier's keys is refused with `deny.workload_unbound` (403), and a registry that cannot be read is UNAVAILABLE (503), never an implicit allow. The principal kind alone grants nothing, so a tenant-created managed API key runs only the workloads its principal is bound for. A revoked binding is final and a re-bind is a fresh incarnation.

### The company of a standalone workload (D6)

A tenant-wide workload binding alone gives a standalone machine no company-selection authority. Its owner declares the company explicitly: `core.access_workload_company_bindings` (tenant, workload binding, company, status, incarnation) names at most one live company per binding, is written only by the same install/bootstrap path as the bindings, and is read by Core alone. A revoked registration stays as history and is never reopened, so a re-registration is a fresh row with a fresh incarnation.

The declaration narrows both halves of the decision. The company list a standalone workload may select is exactly its declared companies intersected with the tenant's active companies, so an unregistered workload selects none (O28); and an admitted workload acts only in the companies its declaration names, so a request that selects another company is refused with `deny.workload_unbound`. The declaration is read on every decision, in the caller's own transaction when there is one (O75). Registration writes and binding revocations take the existing tenant fence exclusively; prepared Actions hold its shared lock through commit, so authority cannot be revoked between the joined recheck and the owner write. No revision or trust bit is invented. Losing the last registration-bearing binding never widens another standalone binding: an empty active-company set denies every company-scoped standalone decision. A verified module subject retains the separate tenant-wide carrier path because its calling module already proved the company; tenant-only workloads do not require company selection.

### Registered workload gateway authority

A version 4 gateway assertion names an independently enrolled system Principal for one exact owner operation. The issuer rule and source operation contract must agree on the receiving entrypoint and schema version. Its signed declaration, entrypoint, version, workload key and Legal Entity scope must match the actual receiving Action or read, including batched gate decisions. Neither a generic module credential nor another capability sharing the same permission key can substitute for that operation.

A nested registered assertion may use an owner-declared conditional operation requirement instead of a module-wide intrinsic dependency. The public server helper checks the exact live Core execution lease, original scope object, genuine consuming registration and current provider contract before sending its requirement key. Shell derives the consuming entrypoint and version from the authenticated incoming assertion, then matches that key to the current manifest's exact consuming entrypoint and provider module, entrypoint and version. An invalid conditional key cannot fall back to an intrinsic declaration. Conditional branches do not add activation dependencies or waive composition cycle checks; their owner still evaluates the branch's condition and evidence in its real handler.

`RegisteredWorkload`, `RegisteredAdmission` and `RegisteredRecovery` may also carry `operationRequirementKey` for an exact source-declared conditional provider. A current worker uses the separate live worker contract fact described in [Outbox Workers](./OUTBOX_WORKERS.md#registered-cross-owner-effects); its handler context cannot be replaced by an Action or Read scope. Shell derives the consuming worker from the validated native delivery and unique registered subscription. A succeeded admission uses its native Action identity and current public Action descriptor. Settled historical recovery uses the durable delivery witness rather than an expired worker lease. No worker schema version or historical admission version is fabricated. These conditional checks supplement the finite issuer rule and all existing authority checks; an absent key retains the intrinsic contract path, while a supplied invalid key always fails closed.

Fresh effects require all of: an active Tenant; the active original integration Principal and its current source admission workload; that original Principal's exact destination owner workload; and exactly one eligible receiving system Principal with the exact destination workload. Shell signs the observed binding incarnations, and Core rechecks them at the receiver. A missing, ambiguous, revoked, changed or unreadable enrollment fails closed. Rotating the original ingress API key does not cancel an already admitted operation: its succeeded admission and current registered authorities govern execution, rather than continued possession or validity of the old credential.

The typed Symmy ingress can derive company scope only from a fresh protected route-context Read through the admitted Symmy release. Shell privately binds that response to the freshly verified integration identity, route selection and composition, checks its current source workload and the company's active Tenant membership, and signs finite route metadata for the exact receiving entrypoints and schema versions inside that request. Only the redeemed, sealed route metadata permits the corresponding integration company scope; ordinary integration assertions still cannot use the human company selector. The receiving gate checks that exact operation, and owner admission rechecks the configured route. Scoped owner reads repeat this route check and require an exact published Read in the route's allowed operations. Request bodies cannot supply this proof, and this path does not change the human company selector.

The system Principal's base identity stays tenant-local. A separate signed company scope must agree with the original admission and the receiving scope declaration; the Legal Entity must still be active in that Tenant. Only Core's exact sealed derived operational context carries this scope. Copying or decoding a look-alike object never manufactures that provenance. Version 4 does not bypass an owner overlay or turn a local `registerSystemWorkload` context into an HTTP capability.

Before a first owner write, the caller persists the intended effective executor Principal with its command plan. Assertion responses expose the non-secret machine Principal and binding incarnation; subsequent issuance supplies `expectedPrincipalId` and rejects a different executor. Ambiguous-response recovery repeats the original command, idempotency key and effective actor. A new enrollment cannot turn that recovery into a fresh ordinary command. Denied original authority never permits a general write or read fallback; any exact historical receipt recovery requires its own explicit narrow owner authorization.

A `RegisteredRecovery` assertion is a distinct Read-only exception to the original-current-write requirement. Its issuer rule names one exact owner receipt Read and the original write Action/job identity. Shell proves the historical permanent tuple (Tenant, original effective Principal, Action, idempotency key and command hash) and the recorded system context of the same live delivery or immutable synchronous admission. The original invocation's company must match its declared scope and admission; an explicitly tenant-only receipt Read may retain its tenant scope. An unexpired source credential alone cannot choose another job or invocation. Current Tenant, independent recovery Principal, exact read workload and binding incarnation remain required; a live-worker recovery also requires its current claim.

An explicitly opted-in `HistoricalDelivery` recovery source supports independent exact receipt reconciliation in any genuine native delivery state, including a settled asynchronous delivery. Shell joins its original delivery, message, versioned public event and succeeded admission, verifies the registered source module and worker, and decodes the matching public job envelope. Its historical command identity uses the actual delivery identifier, never a substituted admission identifier. The supported enrollment uses the public Symmy job-admitted v1 contract and its exact subscription. This witness asserts no live worker or claim and requires no original write permission; current independent Read authority and exact owner receipt constraints still apply. A missing native result remains absence or not found, never a new execution attempt. It is available only inside `RegisteredRecovery` and cannot authorize an Action or reopen a cancelled source fence.

Core rejects this recovery authority before any Action invocation. Before a Read reaches private code, Core checks the actual decoded request's canonical hash and the signed exact read operation. The owner must additionally select and compare the signed original invocation, original Principal and original Action, and return only its permitted minimal receipt projection. Hashing a different receipt request cannot authorize that receipt. Current Privacy and target checks still govern disclosure. An explicitly enrolled recovery-to-Privacy lookup preserves the historical tuple and binds its own exact request hash; it does not restore a revoked original write grant.

A scoped historical fact reader exposes only an exact original invocation identity/status or absence. Workers receive a lifetime-bound version inside their verified tenant scope. This lookup never executes the original command, returns private business payload, or treats an unknown outcome as a new command. Pure owner-published request identity helpers must reproduce the actual Core normalization and authorization target; source business resource references are not a substitute. Action hashes and evidence use the installed operational company while the base system Principal remains tenant-local.

An admitted source that supports cancellation or erasure also opens Core's neutral source execution fence inside its actual admission Action transaction. Every registered owner Action holds a shared lock on that admission's OPEN fence through commit. Cancellation irreversibly closes the fence under an exclusive lock before source data is erased, waiting for actual in-flight owner transactions. A saved or previously minted assertion cannot start another owner effect after cancellation. This fence stores no business payload and grants no permission; independently authorized exact receipt recovery remains Read-only after closure.

A nested owner proof may use `readScopedSourceExecutionFence` inside its exact live Core Read or Action transaction. This nonlocking snapshot returns only the succeeded native admission's identity and fence state in the installed Tenant and Legal Entity. It must not replace the owner Action's commit-bound lock or treat a snapshot as execution authority. Its purpose is to inspect the original source while that outer owner lock is held, without queuing another shared lock behind cancellation.

`readScopedSourceAdmissionEnrollment` adds the original integration's current binding incarnation for an explicitly requested source workload. The owner checks the recorded Action and requested workload against its actual admission descriptor. This is a current enrollment fact, not evidence that the historical gate selected that binding, and it does not inspect the original API key or construct a trusted Principal.

A normal registered Privacy organization-business applicability Read may call the exact Symmy source-organization-facts Read only through its declared conditional requirement and finite issuer rule. This private version 4 path mints a one-use signing witness after verified incoming assertion and native workload admission. The target assertion retains the incoming issue and expiry interval and carries `organizationProcessingRead` with the canonical decoded target request hash. Core requires this marker on that normal version 4 target, checks the actual `PROCESSING` purpose and decoded input hash, and refuses every Action, including a cached replay. It cannot authorize the Governance purpose or continue to another provider. Current source enrollment, original authorities and native claim checks remain required; generic human and API-key Symmy issuance stays refused.

The signed workload tuple fixes the processing Read's exact deployed schema version. The issuer rule and conditional requirement must name that same version in the admitted Composition. The owner sets `accessWorkload.requestPurpose` on the governed Read. Core compares the signed tuple and request hash with the receiving registration and requires the decoded purpose declared there.

### Finite Privacy dispatch authority

Version 5 is a separate, finite human capability for the targeted Privacy-to-Symmy handoff. `PrivacyDispatch` preserves the original human, authentication facts and governance Legal Entity; it neither constructs a system Principal nor clears the company to manufacture Tenant scope. Shell checks the succeeded `privacy.core.dispatch-privacy-measure` invocation and its exact public handoff, native event, message and targeted Symmy delivery against the admitted Composition. Current human identity and the original Privacy dispatch authority in its actual governance company remain required. The existing Symmy Tenant retention and receipt rights still apply, so a company-only grant cannot authorize Tenant retention. The receipt checks unrestricted Tenant list authority for its declared all-scope selector rather than inventing a record target.

The signed operation permits only Symmy retention, its exact receipt Read, Privacy execution eligibility, or recording that owner outcome. Its audience, entrypoint, schema version and canonical request hash must match the actual receiving operation. The finite hash covers the normalized encoded Action payload or decoded Read input; Core's full Action identity and idempotency hash remain separate. A live worker source uses the exact registered handler context and current native claim; every continuation retains that lineage, and receivers recheck it. Retention may call only the declared Privacy eligibility Read, and recording an outcome may call only the declared Symmy receipt Read, through the real current conditional operation lease. Refusals for a resolved human and governance scope use the existing delegated decision evidence path.

A durable dispatch witness is restricted to the exact Symmy receipt Read from the declared Privacy coordinator. It proves the same committed native handoff without inventing an ended worker lease or applying the generic Originator age limit. Current identity, governance authority, module lifecycle and receipt constraints remain required. Generic version 1–4 issuance and the general human Symmy restriction are unchanged; legacy `Assertion` delegation refuses version 5 instead of dropping its finite restrictions. Only the private signer can consume the native evidence module's opaque witness, and possession of a module credential or a copied metadata object supplies no such witness.

The legacy assertion binds to operation schema version 1. For an approved dispatch operation published at a different version, Shell resolves a single version in the pinned Composition, checks any conditional requirement against it, and uses assertion version 7 to sign the exact receiving tuple. A receiver compares that tuple and the request hash with its real registration. The legacy assertion family cannot carry the new tuple, and generic delegation cannot drop version 7 restrictions.

The gateway validates the finite wire policy against the Privacy dispatch Action and worker subscription published in the Composition revision signed into the assertion. The verifier seals those declarations, the approved native subject and access mode, and the receiving tuple into the verified context. Core checks current scope, operation, and native evidence using that sealed policy.

### Human organization governance Read

Version 6 is a separate private `OrganizationGovernanceRead` capability for the existing Symmy organization source-facts Read. It accepts only a genuine version 2 or 3 human Privacy assertion with its original explicit authentication namespace, Tenant and governance Legal Entity, together with the current Privacy module credential and admitted Composition. Version 1 is refused because its omitted namespace cannot prove the current native binding under the existing resolver; no namespace is guessed or added. Workload and finite Privacy-dispatch assertions cannot be converted into this family.

The source owner decodes the published Governance request and supplies its canonical decoded-input hash. That checksum restricts the eventual request and grants no permission. Both private issuance and the receiver require the human's existing SourceFacts Read right in that same governance company. No consuming entrypoint or execution lease is claimed from the incoming human token. The signed metadata permits only the fixed Read and schema version; Core checks its actual decoded request hash and rejects every Action, including a cached Action replay. The owner additionally confines this marker to the Governance purpose and retains its exact admission, safe plan, fence, source-scope and current enrollment checks.

The new assertion has a fresh nonce and redemption grant but retains the source assertion's exact issue and expiry interval. It cannot renew expired source authentication or extend that interval. Generic human Symmy issuance remains refused, and legacy delegation cannot discard version 6 restrictions. Reading source facts neither records a Privacy decision nor grants write authority; the actual Privacy RecordApplicability operation remains independently authorized in its governance company.

The legacy assertion binds to operation schema version 1. For a different version of the same approved organization Read, Shell requires the Privacy applicability Read and RecordApplicability provider declarations in the pinned Composition to name that exact published Symmy version. Shell then uses assertion version 8 to sign the exact receiving tuple. The same human, company, request hash and Read restrictions apply, and legacy delegation cannot discard them.

## Owner overlay

An owner overlay is the owner's own business rule on its own state, never a second permission system. `accessOwnerFacts` (O70) lets a descriptor hand the overlay owner-derived facts such as `{ counterpartyId }`; Core passes them unchanged into the overlay input. The overlay applies owner-local limits (for example per-counterparty grants) and fails closed: a missing fact for a check that needs it denies. Owner facts never reach the engine and never grant.

## Rules for module authors

- Declare every protected entrypoint. Start new descriptors from their Codesmith generator; a protected page uses `defineRouteMeta`.
- Never grant from code. A declaration only creates a catalog entry, and a module never grants anything itself. A new or changed declaration reaches people only through a Role: the tenant's untouched "Plný přístup" preset follows each newly published release by itself (see _Releases and "Plný přístup"_ below), and every other Role uses it only after an administrator adopts its Access change from Novinky. Either way it is usable only through an Assignment.
- Do not add SpiceDB relations, definitions or tuples for a module permission. The engine schema is fixed.
- Do not add new hand-written command or permission lists. Every new command maps to exactly one declared permission.
- Lists filter in the owner's own query using the predicate the decision returns. Never filter after fetching, and never sort or filter by a field the actor cannot read.
- Domain rules such as a locked period, separation of duties or a threshold stay in the module's Policy and run after authorization; they never grant.
- Search providers name the declaration key of their own governed search read in the manifest descriptor `accessKey`.

## Rules for Core

- **Intent and projection.** PostgreSQL holds intent: catalog snapshots, Roles and immutable Role revisions with provenance, Assignment incarnations with end dates, Delegations, Access changes and Adoptions, proposals, Mandates and execution receipts, Agent connections with consent snapshots, and the decision log. SpiceDB is a projection of that intent.
- **One writer.** Only the Core compiler writes the v2 SpiceDB definitions. It compiles levels, switches and templates into exact grant cells, validates a change before taking the Scope fence, records each operation in its own journal, and verifies the complete projection against intent.
- **What the Scope fence protects.** A tenant's fence is held (`Changing`) while one operation projects it, under a lease the holder renews; a projection that failed after it wrote to the engine keeps it closed until the next reconcile completes (the Outbox host's fence sweep takes such fences over once a minute). The fence protects writes: every protected Action locks it and runs only on a `Ready` fence, so nothing commits against a half-written graph, and a second writer never interleaves. It does not protect reads: read and inspection gates do not check it and answer from the graph as it is. Within one projection every revocation is therefore sent before any grant (a new suspension first, a lifted suspension last, since `suspended` is subtracted from access), so a reader can briefly miss a right being granted but never keeps a revoked one beside a new one.
- **Fixed schema.** The v2 definitions follow the reference `schema-v2.2.zed` from #1343. Every v2 name carries an `access_` prefix, `company` becomes `access_legal_entity`, and `principal` is shared with the rest of Core. Configure is structural (scope admins in their own scope, installed or not, plus live delegations inside their envelope); use comes only from grant cells.
- **One decision function.** Single checks, lists, fields, exports, explanations and the agent's tool list all ask the same question: person ∩ agent ∩ Agent connection. Resolve the trusted scope (Legal Entity for company business data, Tenant context for administration), apply the connection ceiling, run one `CheckBulkPermissions` witness chain over the actor's candidate grants, then record predicates, field classes (which require parent record read) and domain rules.
- **Outcomes.** `ALLOWED`, `NEEDS_APPROVAL` or `DENIED`, with `UNAVAILABLE` only for an unprovable engine, transport, deadline or fence failure, mapped as in [Effect Error and HTTP Contracts](./ERRORS.md). Every decision is logged with its reasons, and when an administrator asks about somebody else the row keeps the evaluated principal as its actor and the asker in `on_behalf_of_principal_id`, so the trail separates "explained about X" from "X acted" (O86).
- **Subjects.** The v2 graph accepts only verified humans and `agent`. The compiler maps exactly those two kinds and refuses every other one, so a service, integration or system principal never appears in a v2 tuple. Such a principal keeps its workload classification, which is not an agent, and machine provisioning stays with it.
- **Deadlines.** The admission deadline is the earliest relevant end date of the path used (membership, Assignment, Delegation, Agent connection, task or Mandate). Core enforces it itself, independent of engine caching.
- **Scopes never leak.** A company grant authorizes only that company. Owner and admin status manage access; using it always requires membership and a granted Role. Records never move between companies.
- **Approvals.** Only people approve and administer. A Mandate is single use, lives 24 hours (1 hour for critical), and is re-checked at execution. It binds, in the graph, the approver's exact execution and approval Assignments together with those grants; the requester's exact Assignment is bound in Core and re-checked at execution. It lapses permanently on loss of role, membership, suspension, uninstall or parent read access, and a Role edit that keeps the approver's authority keeps the Mandate. Only the approving human executes it.
- **Lifecycle.** Leaving a company removes every owner, admin, Delegation, Assignment, team and connection right there, and rejoining starts clean. The last owner can never be removed. Uninstall stops every use and keeps configuration; a reinstall never restores something revoked meanwhile.
- **Delegation.** A delegate acts only while the exact Delegation is live, only within its envelope, never on themselves and never further.
- **Novinky.** Catalog snapshot diffs create Access changes. Routine items may be adopted in one batch per release; widening access, sensitive and critical items are reviewed one by one with a named effect. Undo never restores something revoked.
- **Releases and "Plný přístup".** "Plný přístup" covers everything the newest release declares, including everything a later release adds; every other Role, preset or custom, adopts a release only through Novinky. Each deployment's activation publishes its catalog (`topology/authorization-catalog.json`) before the release takes the authority (`scripts/activate-access-catalog-release.mts`, run by the migrator with a time budget; `access/release/activation.ts`). No deployment carries an ordering Core can trust, so content decides, conservatively: a catalog becomes the newest release only when it was never published and it _covers_ the newest release, which means every capability the newest release declares is still declared with at least the same modes and selectors, or is claimed by declared lineage (`renamedFrom`, `splitFrom`). Anything else publishes nothing and changes no tenant, so a removal or a narrowing never reaches a release, and an older deployment that starts again cannot drop or narrow anything the newest release declares; the activation then exits non-zero with a distinct line (see _Release activation: a catalog that is not a successor_). An older deployment that only adds capabilities cannot be told from a newer one; publishing it only adds capabilities no running code uses. A capability a release no longer declares stays in the Roles that hold it and is inert, because the gate decides only the declaration the running code presents. In every active tenant the untouched preset — the tenant-wide Role its bootstrap created (found by its derived id, never its name), still the `full_access` template, with no revision after the first written by anyone but the release actor — then gains an additions-only successor revision pinned to the newest release, so its holders in every company where it is held are granted the new capabilities; a preset a person changed, or one that is not tenant-wide, is a Role like any other and gets Novinky, and the tenant still takes the release. The changes between the release each other Role is pinned to and the newest one are recorded as pending Novinky items. The successor is authored by the tenant's release actor, the one `system` principal whose `platform_role` is `access_release_actor`; it is never a person, holds no Role and is never a v2 subject. Nobody changes a `system` principal's kind, tenant, disabled time or platform role, and its status changes only to archived, once its tenant is archived (`core.keep_system_principals`). The database (`core.require_role_revision_author`) accepts the release actor as an author only for a successor of a tenant-wide Role whose every revision is the `full_access` template and whose every revision after the first the same release actor wrote — so a person's later revision, whatever provenance it claims, ends the follow for good. The successor is pinned to the newest release, keeps every previous cell field for field, and adds only cells of exactly `{capabilityKey, mode, selector: {_tag}}` for capabilities that release declares: a declared mode, a declared selector (`all` only where the capability declares it or declares none), no amount ceiling, in a slot not held yet, each slot once; the follow also holds the activation lock and refuses a release that is no longer the newest. A failed activation keeps the previous release, so new capabilities stay denied; if intent was recorded without its projection, the release access verification stops the boot before the release takes the authority, and the next activation reconciles every tenant.
- **Administration never depends on business scope.** Access administration screens and APIs (Lidé, Role, Novinky, Ke schválení, Proč?) run in Tenant context and work without a selected Legal Entity and without business-data access. Capability keys start with their entrypoint's own module key, so Shell- and Identity-owned surfaces use `core.shell.*` and `core.identity.*`.
- **Reducing authority is never blocked.** Stopping an impersonation, revoking or disabling a credential, leaving a company or declining a proposal is always allowed to its holder, even when the related capability was never adopted. The runtime never hard-codes an Action key for this; a descriptor declares `accessReducesAuthority`.
- **Release activation: a catalog that is not a successor.** When a deployment's catalog drops or narrows something the newest release declares without lineage, the activation publishes nothing, changes no tenant and fails loudly: `ACCESS CATALOG RELEASE ACTIVATION FAILED: the deployed catalog … is not a successor of the newest release <id>: it lacks or narrows <n> of its capabilities (<first keys>, …)`, exit 1, which the migrator reports while the release boots on the previous authorization. It blocks every later deployment that also lacks those capabilities, so it is resolved, never left: run `node scripts/activate-access-catalog-release.mts --dry-run` from the deployed revision to see the same decision and keys. If the catalog came from a stray build (a side branch, a stale artifact, an older revision), deploy the trunk again; nothing in the database changes. If a capability was moved, declare its lineage (`renamedFrom`, `splitFrom`) and deploy again. Only a deliberate removal or narrowing needs a reviewed operator step, which does not exist yet and is described here only: under the activation lock, retire the newest release in favour of the deployed catalog — record the deployed catalog as the newest release, ordered after the retired one, with the reviewer, the reason and the dropped keys written to the release history, and change no Role (cells of a dropped capability stay inert, because the gate decides only the declaration the running code presents). It is never a migration side effect and never automatic.
- **Bootstrap.** A new Tenant gets its scopes, owner membership, a "Plný přístup" Role compiled from the current catalog snapshot, an owner assignment in every scope, and one compiler reconcile. `bootstrapTenantAccess` takes the installed modules' declarations as an explicit input; Core never scans source code.
- **Catalog.** `pnpm authorization:inventory:check` fails on a missing or invalid declaration instead of reporting it. `pnpm authorization:catalog:report` lists the current catalog, including field groups and review findings.
