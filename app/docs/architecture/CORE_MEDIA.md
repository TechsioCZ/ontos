# Core Media

Implementation mechanics of Core Media, the Core-owned system capability that stores one file as a Media Asset and returns the same verified bytes to an authorized caller. The decision (one logical version `V1`, automatically Current, `revision = 1`) is [ADR-0031](../../../docs/adr/0031-core-media-launch-single-version-current.md); authorization is [ADR-0030](../../../docs/adr/0030-granular-authorization.md) and [Granular Authorization](AUTHORIZATION.md). Vocabulary (Core Media, Media Asset, Media Link, ResourceRef, Reconciliation) is defined once in the [OntOS context](../../../docs/contexts/ontos/CONTEXT.md) and is not restated here. Core Media is not a MicroVertical, has no UI, no delete, no version history and no second permission store.

This page describes what is implemented. Rows that have no executed proof against the real object store are named under [Known gaps](#known-gaps).

## Where it lives

| Concern                                                    | Owner                                                                                                                                                                                                      |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actions, Reads, the byte hop, verification, the S3 adapter | `packages/core-runtime/src/media/`, `modules/actions/*asset*.action.ts`, `generated-reads/asset-*.ts` (Core owner, module id `core.media`, resource type `core.media.asset`, resource id = `mediaAssetId`) |
| Table                                                      | `core.media_assets` (and `core.media_links`); no Core migration was added for Core Media; the storage key is derived from the row identity                                                                 |
| HTTP byte edges and the hosted Current operation           | `apps/shell-super-app` (hand-written streaming routes and the Shell-hosted receiver)                                                                                                                       |
| Catalog's use of Current                                   | `verticals/catalog/src/integrations/core-media-owner.ts` (the binding), `catalog-document-current.read.ts`                                                                                                 |

The Shell is the only host that imports the byte surface (`@app/core-runtime/media/edge`). A deployment never imports Core Media tables or private source.

## Entrypoints and declaration keys

Action keys (all `idempotency: required`) and the access declarations they carry:

| Entrypoint                                         | Declaration key                      | Risk and modes                                                 | Carrier                                                                                               |
| -------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Action `core.media.upload-asset` (reserve)         | `core.media.asset.upload`            | routine, run                                                   | human or agent holds the declaration; system, integration and import use workload `core.media.ingest` |
| Action `core.media.confirm-asset`                  | `core.media.asset.confirm`           | routine, run                                                   | as above                                                                                              |
| Action `core.media.rename-display-filename`        | `core.media.display-filename.rename` | routine, run/propose/approve, selector `all`                   | declaration only, no machine carrier                                                                  |
| Action `core.media.record-asset-integrity-failure` | `core.media.asset-integrity.fail`    | routine, run                                                   | workload `core.media.integrity`                                                                       |
| Read metadata                                      | `core.media.asset-metadata.read`     | routine, selector `all`                                        | declaration                                                                                           |
| Read download                                      | `core.media.asset-download.read`     | sensitive, selector `all`, access kind `download`              | declaration                                                                                           |
| Read Current                                       | `core.media.asset-current.read`      | routine, `accessActor` callers `['catalog']`, subject `rights` | module-to-module only                                                                                 |
| Read asset byte source                             | none (`authenticated_principal`)     | n/a                                                            | the reserving principal and the reserved row are the authorization for the byte hop                   |

The generated descriptors are in `topology/authorization-catalog.json` (`pnpm authorization:catalog:artifact:check`). The origin a caller states (`user`, `system`, `integration`, `import`) is recorded provenance and grants nothing. It is cross-checked against the carrier, consistency only (BR-06 of #1430): the reserve Action reads the acting principal's kind from Core identity, and a person or agent may state only `user`, a workload principal (`system`, `integration`, `service`) only `system`, `integration` or `import`. A contradiction, or a principal of unknown kind, is `MediaForbidden` before any row exists. `system`, `integration` and `import` are not told apart (no Core fact distinguishes them), and no origin gains or loses a permission.

HTTP routes (Shell, session authentication, no payload schema for bytes):

- `PUT /core/media/assets/:mediaAssetId/bytes`: the raw bytes of the file reserved as `mediaAssetId`, with an exact `Content-Length` (otherwise `411`). Success is only `processingStatus: ready`. Status meanings are in [Effect Error and HTTP Contracts](ERRORS.md).
- `GET /core/media/assets/:mediaAssetId/content` (and `HEAD`, which answers from the row and reads no provider byte): the verified bytes. `Range` and every conditional header are ignored.
- `POST /core/operations/asset-current`: the Shell-hosted Current read for modules, see below.

The three Actions have Shell client routes, generated by `scaffold:action-http --scope core` (the generator's Core mode is in `scripts/scaffolding/action-http/core.mts`; the owner's own schemas are re-published from `@app/core-runtime/media/upload-contract` and `rename-contract`). All three follow the Shell identity-operation convention: session authentication, a required `Idempotency-Key` header (`428` without it), the saved reply for a same-key retry, the Shell problems (`403`, `404`, `409`, `422`, `503`), and one request body that is the Action's encoded payload.

- `POST /core/actions/upload-asset` (reserve): answers `{ mediaAssetRef, processingStatus: 'uploaded' }`. The id in `mediaAssetRef.resourceId` is the Action invocation's id and is the id the client sends its bytes to.
- `POST /core/actions/confirm-asset` (confirm): the recovery step for a client that sent its bytes and never learned the outcome. Body `{ mediaAssetRef }`. Only the principal that reserved the asset can cause a read-back of the stored object (anyone else gets the answer of an absent asset); the confirm Action then decides under the caller's own `core.media.asset.confirm` capability for every row, a sealed or failed one included. The host-produced evidence is `provideConfirmAssetEvidence` in `api/index.ts` (a request-scoped service no caller may forge). Key semantics: the key identifies one attempt; an attempt that ended uncertain (`503`) is retried under a new key, as the byte edge does for its own confirm.
- `POST /core/actions/rename-display-filename` (rename): `{ mediaAssetRef, displayFilename }`; a holder of `propose` only is refused (`403`) and nothing is renamed.

## Reserve, stream, confirm

1. **Reserve** (`core.media.upload-asset`): creates the `core.media_assets` row in `uploaded` under the Action Invocation's own id. The row fixes the declared size, SHA-256, MIME type, display name and origin; the asset id exists from here but is usable only at `ready`. The storage key is a pure function of `(tenantId, mediaAssetId)` under a fixed domain prefix (`core-media/v1/` plus a hex digest): independent of any file name and never a URL or revision.
2. **Stream** (byte hop, `media/byte-stream.ts`, `ingest.ts`): no Core transaction, lock or connection is held while bytes move. The body is streamed into the provider (never buffered whole), counted and hashed on the way, written create-only. Same-size different bytes, or a body that differs from the reservation, is refused with a conflict and the row stays `uploaded`.

   The byte PUT edge is a ratified boundary (decision 5). It accepts bytes only for a reserved row in `uploaded`, bound to the principal and tenant that reserved it: another principal of the tenant is refused (`403`, the same answer for every row status), another tenant and an unknown id are `404`, a row whose storage key is not the one derived from the named tenant and asset is `404` with no provider call, `failed` and `scanning` rows accept no bytes, and a `ready` row is never written (an identical replay is answered from the sealed identity, a different body is `409`). The provider is handed at most the reserved size, whatever the body and its stated `Content-Length` claim. The accepted risk is that the byte hop is not a permission: the bytes (reserved size at most, unreadable, unsealed) are written before the confirm capability is decided, so a principal whose capability was revoked after reserve can still write them and then cannot seal them.

3. **Confirm** (`core.media.confirm-asset`): runs inside the edge under the caller's own principal after the stored object is read back and verified against the reserved identity (`StoredMediaObjectVerification`). Only this Action seals the row (`ready`, with the actual size and SHA-256). A retry after an uncertain end completes the original asset, never a second one.

Each stored object is addressed by its derived key only; the key, provider id, version reference and any URL never reach a response, log or error. A new upload is always a new Media Asset id.

## Verified read and failed versus unavailable

`media/verified-read.ts` is the single place that classifies what a provider returns for a `ready` asset. Outcomes:

- `verified`: the delivered bytes equal the sealed size and SHA-256.
- `unavailable`: this request could not be judged (provider failure, short or doubtful end of stream, object changed while read). Never durable, never promoted by time, never corruption.
- `missing_object`: the provider holds nothing under the key. Neither an absent asset nor proof of corruption.
- `inconsistent_metadata`: the row is not a sealed `ready` identity, or (stream mode) the provider's own stat already disagrees; delivery is refused before a byte.
- `integrity_failed`: proven corruption only: the whole object was read, the stream ended with the length the provider declared, the object did not change meanwhile, and its size or SHA-256 differs from the sealed identity.

Proven corruption is handed to `core.media.record-asset-integrity-failure` (the only writer of `failed`, conditional on the sealed identity). A read never changes status.

## Recovery

Recovery is client or workload driven; there is no scheduler, timer, retry loop, attempt count or deadline in Core Media code (guard test `core-media-recovery-guards`).

- `reconcileUncertainUpload` settles an uncertain upload against the original asset row: `completed`, `closed_failed` (only when the confirm Action proves a mismatch) or `unresolved` (nothing proven; the same client may resend to the same asset).
- A new independent upload may start only after a confirmed failure; `mayStartIndependentUpload` is the check and has no production caller (advisory).
- `cleanup-eligibility.ts` is a check only; nothing removes objects. The S3 adapter's only HTTP `DELETE` aborts its own unfinished multipart upload.
- Recovery logging uses a closed vocabulary and a redacted reference, never keys, bytes, URLs or credentials.

## Download edge

`GET .../content` runs, on every request, the governed `core.media.asset-download.read` (authorization, module state, evidence all fresh), then opens the stored object and streams it through the verifier (`media/download.ts`).

- **Verify while streaming**: the SHA-256 is computed with the platform's native `DigestStream` while streaming; the last chunk is withheld until the verdict. A mismatch or failed read after the first byte aborts the response without a clean end (`MediaDownloadAborted`); the client must treat a body that does not end cleanly as failed.
- **Before the first byte**: `MediaNotReady` (conflict), `MediaUnavailable` (provider or doubtful framing, retryable `503`) or `MediaIntegrityFailed` (`422`).
- **Per-request authorization**: nothing (URL, ticket, token, cache entry, decision) outlives a request. A transfer authorized at its start may finish after the Permission is revoked; the next request or a reconnect is a new decision.
- **Headers** are an allow-list built from the row: `Cache-Control: private, no-store`, `Content-Disposition: attachment` with a sanitized name (control and bidirectional characters and separators replaced, length bounded) and an RFC 5987 UTF-8 form, exact `Content-Length`, `X-Content-Type-Options: nosniff`, a sandboxing `Content-Security-Policy`, and `Content-Type` only if the recorded value is a plain `type/subtype`. No provider header, ETag or range support is exposed.

## Current V1, Shell-hosted receiver and Catalog binding

`core.media.asset-current.read` answers per requested reference, in request order: `AVAILABLE` (`revision = 1`, a constant derived from the asset, never the provider version reference and never a `revisionId`) only for a `ready`, sealed asset whose stored object the provider confirms by a stat (size and the version pin recorded at confirm; no bytes are read); `ABSENT` for no row or another tenant's id; `UNAVAILABLE` when the provider cannot answer; `CURRENT_UNVERIFIED` for everything else. A caller without the capability is refused for the whole call (the consumer reports it as `FORBIDDEN`).

The object store credential lives only in the Shell host. A module reaches Current by relaying its requester as an audience-scoped gateway assertion to `POST /core/operations/asset-current`: the Shell verifies the assertion, consumes its `jti` once in the Shell-private table `auth.gateway_assertion_redemptions`, checks that the calling module's installed release declares a Shell-hosted person requirement, and runs the Read as the requester. Catalog's binding (`core-media-owner.ts`) turns the answer into `CatalogDocumentAvailability`: it returns exactly one entry per requested reference, refuses to promote anything to `AVAILABLE` that Core did not mark so, and fails the whole read when Core's answer is incomplete or mismatched. The Catalog Current contract shape is unchanged. **The requester's selected company narrows Current.** `catalogDocumentCurrentRead` is `legalEntityScope: 'optional'` and Catalog's Core Media requirement relays the requester as the `subject` (`callers: [{ kind: 'person', legalEntityScope: 'subject' }]`), so the company a requester selected reaches Core's Current read, whose repository then shows that company's own and company-less assets only: another company's asset answers `ABSENT`, exactly what an asset that never existed answers, and its availability is not revealed. A requester with no company selected is the whole tenant (the platform rule of an `optional` company), so every company's assets answer. The company is only a narrowing of rows, never an authorization input: the gate still decides on the requester's own Current right. The two declarations change together; `catalog-core-media-boundary` fails if only one does. Two boundary decisions behind this path are approved: the Shell-private table `auth.gateway_assertion_redemptions` and its migration (see [Database Trust Boundaries](DATABASE_TRUST_BOUNDARIES.md)), and naming `catalog` in the Read's `accessActor` allow-list (`callers: ['catalog']`, subject `rights`), which adds no permission: the requester must hold the capability themselves.

## S3 provider configuration

The adapter is provider-neutral S3 (SigV4, path or virtual-host addressing) in `media/s3-object-storage.ts`, behind the `ObjectStorage` port. Keys (names only; values come from the platform secret and configuration path, never the repository): `CORE_MEDIA_S3_ENDPOINT`, `CORE_MEDIA_S3_BUCKET`, `CORE_MEDIA_S3_REGION`, `CORE_MEDIA_S3_ADDRESSING_STYLE` (`path` or `virtual-host`), `CORE_MEDIA_S3_CONDITIONAL_CREATE` (`supported` or `unsupported`), `CORE_MEDIA_S3_ACCESS_KEY_ID`, `CORE_MEDIA_S3_SECRET_ACCESS_KEY`, and optional `CORE_MEDIA_S3_PART_SIZE_BYTES`, `CORE_MEDIA_S3_REQUEST_TIMEOUT_MS`. One further optional key sits beside them but is not part of the provider identity: `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS` (see the digest step guard below). The endpoint must be an `https` origin (`http` only on a loopback host). Configuration that fails to parse falls back to an object store that refuses every operation. Credentials are redacted values and appear in no error or log. No retry, backoff or timeout default exists; the timeout applies only when configured.

## Measured limits (facts, not product caps)

No product size limit, MIME allowlist or retry policy is defined by Core Media. Facts and their sources:

| Fact                            | Value                                                                                                                  | Source                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| S3 multipart structure          | minimum part 5 MiB, at most 10,000 parts, all parts but the last equal                                                 | S3 protocol; `s3-config.ts`, `s3-object-storage.ts`                |
| Request body without length     | refused (`411`) by the edge; a stream body without length is not accepted by node `fetch` or workerd against MinIO     | measured 2026-11-20 against the emulator (probe and workerd spike) |
| Adapter memory (node, emulator) | peak growth about 114 MiB for 64 MiB and for 1 GiB objects (bounded, not proportional)                                 | measured 2026-11-20, MinIO emulator                                |
| Native digest on workerd        | 64 MiB hashed in 289 ms wall; a JavaScript hash needs about 1.4 s for the same bytes                                   | measured 2026-11-20, local workerd                                 |
| Worker CPU class (Shell)        | 200 ms; not measurable on local workerd                                                                                | NOT VERIFIED                                                       |
| Digest step guard               | 5 seconds per digest step (one chunk write or the final close), not per object; a technical guard, not a product limit | `media/content-digest.ts`; `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS`     |
| Cloudflare R2 limits            | documented upstream (for example 1 write per second per key, multipart rules)                                          | provider documentation only; no R2 run                             |

**The digest step guard is not a maximum object size.** `DigestStepTimeout` (default 5 s, a `Context.Reference` read at the moment of each step) wraps exactly two platform calls of `ContentDigest`: `add`, one `writer.write` of one chunk, and `finish`, the `close` plus the digest read. It never spans the object: the unit test `core-media-content-digest` drives six steps of 30 ms under a 100 ms guard and none is stopped, and a step that never answers dies at the guard. Setting it needs `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS` (a positive integer of milliseconds) provided through `mediaDigestStepTimeoutLayer`; unset keeps 5 s. The Shell provides it beside the object store (`coreMediaObjectStorageLive`), so the download, the byte PUT and the generated confirm route read it; a malformed value does not stop the host: it logs `core.media.digest-step-timeout.invalid` with the failure reason and the built-in 5 s applies. A step that exceeds the guard is an unexpected defect, never proven corruption: the byte PUT and the confirm answer a 500 problem, a download whose first chunk is still waiting for its digest step closes without a complete body, and the asset stays as it was (`uploaded` or `ready`, never `failed`), so the same request succeeds once the platform answers in time (its end-to-end proof is in the last pull request of the stack). `openVerifiedMediaStream` carries the guard of its request into the returned body, because the transport runs that body in its own context. For scale only: at the measured 64 MiB in 289 ms (about 221 MiB/s) one step would have to carry roughly 1.1 GiB to need 5 s, and the chunks a transfer hands to the digest are the transport's, not the object's. What is **not** measured and so not claimed: the longest `close` after a very large object on a deployed Worker, any object above the 1 GiB node memory run, and whether `close` waits for queued hashing proportional to the queue. If a product maximum object size is wanted it must be decided by its owner from a measurement on the real Worker and the real provider (the largest object that completes reserve, stream, confirm and a verified download within the deployed CPU and ingress limits); this page proposes no number.

## Known gaps

- **No run against Cloudflare R2 or Wasabi.** Credentials were not supplied; every provider behaviour was executed only against the MinIO S3-compatible emulator, which is never evidence for R2.
- **The Catalog chain is not executed end to end.** The Shell receiver and the Core read were run together with a real issued assertion; the Catalog read runtime, assignments and SDK route were not in that world.
- **Existing environments do not receive the capabilities** because the published authorization release is pinned and no code publishes a later one; a fresh database does. This is out of scope for D20 and is raised as its own issue (draft: `release-adoption-issue-draft.md` in the plan folder, not filed).
- **The client routes have no UI.** Reserve, confirm and rename are HTTP routes and a typed client operation (`executeUploadAsset`, `executeConfirmAsset`, `executeRenameDisplayFilename` in `src/api/auth-client.ts`); no page calls them (UI is out of scope).
- **The receiver's caller check admits any Shell-hosted person requirement.** `callingModuleDeclaresHostedOperation` in `apps/shell-super-app/api/core-hosted-operations.ts` accepts a calling module whose release declares a `person` requirement on any Shell-hosted Core provider, not the exact operation being served. Equivalent today because one operation is hosted; once a second one exists, a module that declared operation X could reach operation Y at this gate. The `accessActor` allow-list on the Read (`callers: ['catalog']`, gate `deny.actor_unbound` / `actor_forbidden`) is the real second barrier, which makes it latent. Recorded as a follow-up for the Shell owner; not changed here.
- **Other owners (UNVERIFIED, nothing here is claimed as checked):** production Privacy and retention assessment and physical deletion belong to their owners. Provider-side backup or replication (Wasabi is the probable backup target) needs a named operations owner; a backup copy extends retention beyond the primary object; and the Privacy owner must define, before production, what erasure means for the primary object and for every backup copy. None of this was configured, run or verified in D20.
