# Core Media

Implementation mechanics of Core Media, the Core-owned system capability that stores one file as a Media Asset and returns the same verified bytes to an authorized caller. The decision (one logical version `V1`, automatically Current, `revision = 1`) is [ADR-0031](../../../docs/adr/0031-core-media-launch-single-version-current.md); authorization is [ADR-0030](../../../docs/adr/0030-granular-authorization.md) and [Granular Authorization](AUTHORIZATION.md). Vocabulary (Core Media, Media Asset, Media Link, ResourceRef, Reconciliation) is defined once in the [OntOS context](../../../docs/contexts/ontos/CONTEXT.md) and is not restated here. Core Media is not a MicroVertical, has no UI, no delete, no version history and no second permission store.

This page describes what is implemented. Rows that have no executed proof against the real object store are named under [Known gaps](#known-gaps).

## Entrypoints and declaration keys

Action keys (all `idempotency: required`) and the access declarations they carry:

| -------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Action `core.media.upload-asset` (reserve)         | `core.media.asset.upload`            | routine, run                                                   | human or agent holds the declaration; system, integration and import use workload `core.media.ingest` |
| Action `core.media.confirm-asset`                  | `core.media.asset.confirm`           | routine, run                                                   | as above                                                                                              |
| Action `core.media.rename-display-filename`        | `core.media.display-filename.rename` | routine, run/propose/approve, selector `all`                   | declaration only, no machine carrier                                                                  |
| Action `core.media.record-asset-integrity-failure` | `core.media.asset-integrity.fail`    | routine, run                                                   | workload `core.media.integrity`                                                                       |
| Read metadata                                      | `core.media.asset-metadata.read`     | routine, selector `all`                                        | declaration                                                                                           |
| Read download                                      | `core.media.asset-download.read`     | sensitive, selector `all`, access kind `download`              | declaration                                                                                           |
| Read Current                                       | `core.media.asset-current.read`      | routine, `accessActor` callers `['catalog']`, subject `rights` | module-to-module only                                                                                 |
| Read asset byte source                             | none (`authenticated_principal`)     | n/a                                                            | the reserving principal and the reserved row are the authorization for the byte hop                   |

An upload needs two capabilities, `core.media.asset.upload` to reserve and `core.media.asset.confirm` to seal, so grant them together: a holder of upload alone gets `403` at confirm. Metadata read, download and rename carry a declaration only, so a bound machine principal is refused there (`deny.workload_forbidden`): an integration can upload and confirm but not read. The access gate refuses an agent upload, confirm, metadata read and rename today, even with a role that grants them (`deny.agent_forbidden`).

The generated descriptors are in `topology/authorization-catalog.json` (`pnpm authorization:catalog:artifact:check`). The origin a caller states (`user`, `system`, `integration`, `import`) is recorded provenance and grants nothing. It is cross-checked against the carrier, consistency only (BR-06 of #1430): the reserve Action reads the acting principal's kind from Core identity, and a person or agent may state only `user`, a workload principal (`system`, `integration`, `service`) only `system`, `integration` or `import`. A contradiction, or a principal of unknown kind, is `MediaForbidden` before any row exists. `system`, `integration` and `import` are not told apart: no principal kind identifies `import` and a `service` principal has no origin of its own, so only the consistency with the carrier is checked. No origin gains or loses a permission.

HTTP routes (Shell, session authentication, no payload schema for bytes):

- `PUT /core/media/assets/:mediaAssetId/bytes`: the raw bytes of the file reserved as `mediaAssetId`, with an exact `Content-Length` (otherwise `411`). Success is only `processingStatus: ready`. Status meanings are in [Effect Error and HTTP Contracts](ERRORS.md).
- `GET /core/media/assets/:mediaAssetId/content` (and `HEAD`, which stats the stored object and reads no provider byte: `503` for a missing object, another size or an unavailable or unconfigured store, even where `GET` would read the whole object and prove corruption with `422`): the verified bytes. `Range` and every conditional header are ignored.
- `POST /core/reads/asset-metadata`: the metadata read.
- `POST /core/operations/asset-current`: the Shell-hosted Current read for modules, see below.

The three Actions have Shell client routes, generated by `scaffold:action-http --scope core` (the generator's Core mode is in `scripts/scaffolding/action-http/core.mts`; the owner's own schemas are re-published from `@app/core-runtime/media/upload-contract` and `rename-contract`). All three follow the Shell identity-operation convention: session authentication, a required `Idempotency-Key` header (`428` without it), the saved reply for a same-key retry, the Shell problems (`403`, `404`, `409`, `422`, `503`), and one request body that is the Action's encoded payload.

- `POST /core/actions/upload-asset` (reserve): answers `{ mediaAssetRef, processingStatus: 'uploaded' }`. The id in `mediaAssetRef.resourceId` is the Action invocation's id and is the id the client sends its bytes to.
- `POST /core/actions/confirm-asset` (confirm): the recovery step for a client that sent its bytes and never learned the outcome. Body `{ mediaAssetRef }`. Only the principal that reserved the asset can cause a read-back of the stored object (anyone else gets the answer of an absent asset); the confirm Action then decides under the caller's own `core.media.asset.confirm` capability for every row, a sealed or failed one included. The host-produced evidence is `provideConfirmAssetEvidence` in `api/index.ts` (a request-scoped service no caller may forge). Key semantics: the key identifies one attempt; an attempt that ended uncertain (`503`) is retried under a new key, as the byte edge does for its own confirm.
- `POST /core/actions/rename-display-filename` (rename): `{ mediaAssetRef, displayFilename }`; a holder of `propose` only is refused (`403`) and nothing is renamed.

## Reserve, stream, confirm

1. **Reserve** (`core.media.upload-asset`): creates the `core.media_assets` row in `uploaded` under the Action Invocation's own id. The row fixes the declared size, SHA-256, MIME type, display name and origin (the size and SHA-256 are required of the client, and until the row is sealed they are the uploader's claim, which every reader ignores); the asset id exists from here but is usable only at `ready`. The storage key is a pure function of `(tenantId, mediaAssetId)` under a fixed domain prefix (`core-media/v1/` plus a hex digest): independent of any file name and never a URL or revision. A declared size above what the object store's protocol can write (S3: 10,000 parts of 5 GiB, about 48.8 TiB) is refused `422` (`media_too_large`) before any row exists; that is the provider's limit, and Core states no product size limit.
2. **Stream** (byte hop, `media/byte-stream.ts`, `ingest.ts`): no Core transaction, lock or connection is held while bytes move. The body is streamed into the provider (never buffered whole), counted and hashed on the way, written create-only where the deployment states the provider honours `If-None-Match: *` (`CORE_MEDIA_S3_CONDITIONAL_CREATE=supported`; with `unsupported` a write can replace an object under the key). Same-size different bytes, or a body that differs from the reservation, is refused with a conflict and the row stays `uploaded`.

   The byte PUT edge is a ratified boundary (see [Recorded decisions](#recorded-decisions)). It accepts bytes only for a reserved row in `uploaded`, bound to the principal and tenant that reserved it: another principal of the tenant, another tenant and an unknown id are all `404`, as at confirm, a row whose storage key is not the one derived from the named tenant and asset is `404` with no provider call, `failed` and `scanning` rows accept no bytes, and a `ready` row is never written. A request on any row past `uploaded` first runs the confirm Action, so a caller without the confirm capability is refused (`403`) before a byte is read or anything of the row is told; then `failed` is `422`, `scanning` is `409`, and on `ready` an identical body is answered from the sealed identity and a different one is `409`. The provider is handed at most the reserved size, whatever the body and its stated `Content-Length` claim. The accepted risk is that the byte hop is not a permission: the bytes (reserved size at most, unreadable, unsealed) are written before the confirm capability is decided, so a principal whose capability was revoked after reserve can still write them and then cannot seal them.

3. **Confirm** (`core.media.confirm-asset`): runs inside the edge under the caller's own principal after the stored object is read back and verified against the reserved identity (`StoredMediaObjectVerification`). Only this Action seals the row (`ready`, with the actual size and SHA-256). A retry after an uncertain end completes the original asset, never a second one.

Each stored object is addressed by its derived key only; the key, provider id, version reference and any URL never reach a response, log or error. A new upload is always a new Media Asset id.

## Verified read and failed versus unavailable

`media/verified-read.ts` is the single place that classifies what a provider returns for a `ready` asset. Outcomes:

- `verified`: the delivered bytes equal the sealed size and SHA-256.
- `unavailable`: this request could not be judged (provider failure, short or doubtful end of stream, object changed while read). Never durable, never promoted by time, never corruption.
- `missing_object`: the provider holds nothing under the key. Neither an absent asset nor proof of corruption.
- `inconsistent_metadata`: the row is not a sealed `ready` identity, or (stream mode) the provider's own stat already disagrees; delivery is refused before a byte.
- `integrity_failed`: proven corruption only: the whole object was read, the stream ended with the length the provider declared, the object did not change meanwhile, and its size or SHA-256 differs from the sealed identity.

Proven corruption is handed to `core.media.record-asset-integrity-failure` (the only writer of `failed`, conditional on the sealed identity). A read never changes status.

The Shell host closes this loop when a download proves corruption: its recorder resolves the tenant's single active `system` principal bound to the workload `core.media.integrity` (`SystemPrincipalContextResolver.resolveEnrolled`) and runs the Action as that principal. The workload gate admits it (proven by the Shell end-to-end suite), and because `core.media.integrity` is declared only by this one Action, a principal bound to that key alone can mark an asset `failed` and nothing else: it is refused rename, Current and every other capability, and it holds no read or write of bytes or metadata. The operator must bind that principal to this key only (the resolver picks any active `system` principal bound to the key, and a principal also bound to another workload key keeps that workload's reach). A tenant with no (or an ambiguous) enrolment aborts the transfer as before, logs `core.media.integrity.unrecorded` and leaves the row `ready`. What the enrolment is, how a tenant administrator makes it and how to read a missing one is in "Enrolling the integrity principal" below; nothing was enrolled on any shared environment. **Same-length substitution that nobody downloaded (closed where the provider reports a content-derived ETag, lane 14):** Current reads no byte, so size alone cannot see it. The confirm step records the technical pin of the object whose digest it verified (`storageObjectVersionRef`, taken from the very read-back), and Current compares that pin with the provider's stat. The S3 adapter's pin is the provider's `x-amz-version-id`, or, where the bucket has none (R2 and the MinIO emulator are unversioned by default), `etag:<ETag>`. An ETag that is a content hash (plain MD5 for one `PutObject`, the hash of the part hashes with its part count for a multipart upload) changes when the object under the key is written again with other bytes, so Current answers `CURRENT_UNVERIFIED` (`object_replaced`), writes nothing and leaves the row `ready`; only a download that reads the bytes can prove corruption and close it as `failed`. The pin is integrity evidence only: never a revision, never exposed, never part of the sealed identity. Executed against the MinIO emulator (a single-PUT object swapped out of band in the Shell end-to-end suite; single and multipart ETags equal between a read and a stat), **not R2**. **Not closed:** (1) a row confirmed without a pin (confirmed before pins were recorded, or a provider that answers no ETag) is compared on size only, and a same-length substitution still reads `AVAILABLE`; (2) a provider whose ETag is not derived from the content (some encrypted stores) or is not equal between a read and a stat gives no guarantee, and an unstable one ends confirms and downloads as `unavailable`, never as corruption; (3) whoever can make the provider report the recorded ETag with other bytes, for example a same-length MD5 collision against a plain MD5 ETag, is not detected until a download hashes the bytes with SHA-256; (4) a swap after Current answered is seen only by the next Current or download; (5) the check is fail-closed in the other direction too: the same bytes written again by another path (another part size, a copy or a restore) change the ETag, so Current answers `CURRENT_UNVERIFIED` for a healthy asset, and nothing re-pins the row (a download still verifies it). That path has no owner or test here.

## Enrolling the integrity principal

**What it is for.** When a download proves that a stored object no longer matches what was uploaded, Core Media must mark the asset `failed`. The person downloading may not hold that right, so the Shell does it as a machine identity of that tenant: one `system` principal bound to the workload `core.media.integrity`. Without it nothing breaks for users: the damaged download is still stopped, but the asset stays `ready` and is not recorded as damaged. It is needed once per tenant and per environment, and never for a person.

**What a correct enrolment is.** In the tenant: exactly one principal of kind `system`, status `active`, holding exactly one active workload binding, for `core.media.integrity` and no other key. It needs no role, no assignment and no API key. Do not bind the same principal to other workloads: it would keep their reach. Two eligible principals for the key make the tenant ambiguous and nothing is recorded. To check it, ask for a read-only listing of the tenant's principals bound to the key (`core.access_workload_bindings` joined to `core.principals` on tenant and principal): one row, `kind = system`, both statuses `active`, and that principal's only bound key is `core.media.integrity`.

**How it is made: a tenant administrator enrols it through Core.** Run the Core admin Action `core.identity.change-system-workload-enrollment` with `{ _tag: 'ENROLL', moduleKey: 'core.media', workloadKey: 'core.media.integrity', reason }`. It needs the capability `core.identity.system-workload-enrollment.change` (a tenant administrator; the "Plný přístup" role of a tenant owner holds it. It is critical and part of full access on a fresh database; the principal it creates holds no credential, and the integrity Action additionally needs a proof only the Shell composes), and it creates the tenant's one `system` principal bound to that key alone, which is exactly the correct enrolment above. `END` with the same key revokes the binding and archives the principal for good; a later `ENROLL` creates a new one. Core declares `core.media` and its one system workload in `packages/core-runtime/src/modules/core-system-workloads.ts`, so the Action needs no installed module contract and no `core.media` tenant module state for it (a tenant has an active `core.media` module state from the stage install, and the enrolment does not read it). A key under `core.media` that this declaration does not list is refused, and an `ENROLL` repeated for a tenant that already holds the principal answers `ALREADY_ENROLLED` and changes nothing. After it, verify with the read-only listing above. Proven by the Shell end-to-end suite `core-media-e2e-integrity-enrolment`, whose last scenario runs the real Action as the tenant's owner with an empty installed catalog and `core.media`'s module state removed, and then records proven corruption as `failed`, executed against the MinIO emulator, not R2.

What does not enrol it, and why the Action is the only way:

- The stage accounts file refuses the key in a `workloads` entry: that entry binds an account principal (a person), and the Shell resolves only a `system` principal. A stage file that still names it must drop the entry.
- `core.identity.create-non-human-principal` creates `integration` and `service` principals only, never `system`, and the generic workload binding writer refuses a `system` principal. The Action is the only writer of one.
- The local development seed (`pnpm local:initialize`) creates no integrity principal, because the Action needs a running Shell. Once the applications are up, `pnpm local:enrol-integrity` signs in as the local owner and runs that same `ENROLL` through `POST /auth/identity/system-workload-enrollments` (`ALREADY_ENROLLED` on a rerun). The Shell needs an active Application Composition source (`ONTOS_ACTIVE_APPLICATION_COMPOSITION_URL`, see [Deployment](DEPLOYMENT.md)); plain local setup configures none, and the command then reports the Shell's `503`. A local tenant nobody enrolled records nothing.
- The Shell end-to-end suite's other scenarios enrol with the fixture `enrolSystemWorkload` (`tests/support/core-media-e2e-fixture.ts`), which is test SQL against a throwaway database and not a tool; they prove what the Shell does with an enrolment.

**How a missing or wrong enrolment shows up.** The reader sees a damaged download stop short. The operator sees a warning line `core.media.integrity.unrecorded` carrying the annotation `failure`, preceded by an `integrity` event of `core.media.recovery` with category `unresolved` and the redacted reference of the object (no key, no bytes). `failure: SystemPrincipalContextDeniedError` means the tenant has none, more than one, or a principal that is not an active `system` principal with an active binding (a service principal, a disabled one, a revoked binding). `SystemPrincipalContextUnavailableError` means the database could not be read, and `SystemPrincipalContextInvalidError` that the resolver refused its own input. Any other value names the refusal of the integrity Action itself. The asset stays `ready` and the same download records it as `failed` once exactly one correct enrolment exists. Proven by the Shell end-to-end suite `core-media-e2e-integrity-enrolment` (no principal, a service principal, a disabled one and a revoked binding each record nothing and log the denial; the exact principal then records the same corruption; and a principal enrolled through the `ENROLL` Action records it too), executed against the MinIO emulator, not R2.

## Recovery

Recovery is client or workload driven; there is no scheduler, timer, retry loop, attempt count or deadline in Core Media recovery code (guard test `core-media-recovery-guards`). The one exception is the digest step guard below, a technical guard on a single platform call.

- `reconcileUncertainUpload` settles an uncertain upload against the original asset row: `completed`, `closed_failed` (the confirm Action proves a mismatch, or the row is already `failed`) or `unresolved` (nothing proven; the same client may resend to the same asset).
- A new independent upload may start only after a confirmed failure. This is the client's obligation: Core cannot link two independent idempotency keys, so a `reserve` under a new key is a new asset.
- Core removes no object: the provider port has no delete and no Action removes bytes (the S3 adapter's only HTTP `DELETE` aborts its own unfinished multipart upload). **Abandoned temporary objects** are removed only by a separately approved operator procedure, and only when every condition holds for the one object: its key is the one derived from the named tenant and asset id; no Media Asset row (`ready`, `uploaded`, `scanning` or `failed`) holds that storage identity or id; no media link, evidence reference or Action invocation names it; the provider records no retention or hold, and that absence is confirmed rather than assumed; and the person acting holds the existing technical authority. Anything unproven keeps the object. Because every object Core writes belongs to a reserved asset row, this applies only to objects no Core intent ever created.
- The byte hop never stores bytes that differ from the reservation, so a mismatch at upload arises only from a change made at the provider. A row left `uploaded` whose reserving principal is gone never ends, and no operator path settles it.
- Recovery logging uses a closed vocabulary and a redacted reference, never keys, bytes, URLs or credentials.

## Download edge

`GET .../content` runs, on every request, the governed `core.media.asset-download.read` (authorization, module state, evidence all fresh), then opens the stored object and streams it through the verifier (`media/download.ts`).

- **Verify while streaming**: the SHA-256 is computed with the platform's native `DigestStream` while streaming; the last chunk is withheld until the verdict. A mismatch or failed read after the first byte aborts the response without a clean end (`MediaDownloadAborted`); the client must treat a body that does not end cleanly as failed.
- **Before the first byte**: `MediaNotReady` (conflict), `MediaUnavailable` (provider or doubtful framing, retryable `503`) or `MediaIntegrityFailed` (`422`).
- **Per-request authorization**: nothing (URL, ticket, token, cache entry, decision) outlives a request. A transfer authorized at its start may finish after the Permission is revoked; the next request or a reconnect is a new decision.
- **Headers** are an allow-list built from the row: `Cache-Control: private, no-store`, `Content-Disposition: attachment` with a sanitized name (control and bidirectional characters and separators replaced, length bounded) and an RFC 5987 UTF-8 form, exact `Content-Length`, `X-Content-Type-Options: nosniff`, a sandboxing `Content-Security-Policy`, and `Content-Type` only if the recorded value is a plain `type/subtype`. No provider header, ETag or range support is exposed.

## Current V1, Shell-hosted receiver and Catalog binding

**The Catalog port of #1443.** The issue asked to keep `CatalogDocumentOwnerAvailabilityPort.readCurrentAvailability` and replace only its production `unavailableOwner`. The port and its service tag were removed instead. The read now runs in three steps (read the assignments, call Core with no transaction open, re-read and prove the assignment set revision unchanged), which the port's single call did not express, and the call itself is the declared Core operation, so the adapter (`coreMediaOwnerAvailability`) is the binding and nothing consumed the port. `target` is no longer sent to the owner. Catalog's public response shape is unchanged.

`core.media.asset-current.read` answers per requested reference, in request order: `AVAILABLE` (`revision = 1`, a constant derived from the asset, never the provider version reference and never a `revisionId`) only for a `ready`, sealed asset whose stored object the provider confirms by a stat (size and the pin recorded at confirm: the provider's version id, or its ETag where there is no version id; no bytes are read); `ABSENT` for no row or another tenant's id; `UNAVAILABLE` when the provider cannot answer; `CURRENT_UNVERIFIED` for everything else. A caller without the capability is refused for the whole call (the consumer reports it as `FORBIDDEN`). The capability is tenant-wide, with no per-asset selector, so there is no per-asset `FORBIDDEN`: a holder who selected no company learns the availability of any asset id of the tenant.

The object store credential lives only in the Shell host. A module reaches Current by relaying its requester as an audience-scoped gateway assertion to `POST /core/operations/asset-current`: the Shell verifies the assertion, consumes its `jti` once in the Shell-private table `auth.gateway_assertion_redemptions`, checks that the calling module's installed release declares a person requirement on exactly the operation this route serves (provider module, entrypoint key and schema version, taken from the served registration `assetCurrentRead` and never from the request, so a module that declares another Shell-hosted operation, or this one at another schema version, is refused), and runs the Read as the requester. Catalog's binding (`core-media-owner.ts`) turns the answer into `CatalogDocumentAvailability`: it asks once per distinct Resource, judges each entry at the place of its own request (never re-pairing entries by identity) and refuses to promote anything to `AVAILABLE` that Core did not mark so for that very reference. An entry naming another reference is that assignment's `RESOURCE_MISMATCH`. A request with no entry is `OWNER_CHECK_REQUIRED` in Catalog's projection; the public Current response has no such kind, so the read answers unavailable. Entries nobody asked for, and a missing, rejected or unavailable call, fail the whole read; a refused call is `FORBIDDEN` for every reference. The Catalog Current contract shape is unchanged. **The requester's selected company narrows Current.** `catalogDocumentCurrentRead` is `legalEntityScope: 'optional'` and Catalog's Core Media requirement relays the requester as the `subject` (`callers: [{ kind: 'person', legalEntityScope: 'subject' }]`), so the company a requester selected reaches Core's Current read, whose repository then shows that company's own and company-less assets only: another company's asset answers `ABSENT`, exactly what an asset that never existed answers, and its availability is not revealed. A requester with no company selected is the whole tenant (the platform rule of an `optional` company), so every company's assets answer. The company is only a narrowing of rows, never an authorization input: the gate still decides on the requester's own Current right. The two declarations change together; `catalog-core-media-boundary` fails if only one does. Two boundary decisions behind this path are approved: the Shell-private table `auth.gateway_assertion_redemptions` and its migration (see [Database Trust Boundaries](DATABASE_TRUST_BOUNDARIES.md)), and naming `catalog` in the Read's `accessActor` allow-list (`callers: ['catalog']`, subject `rights`), which adds no permission: the requester must hold the capability themselves.

## S3 provider configuration

The adapter is provider-neutral S3 (SigV4, path or virtual-host addressing) in `media/s3-object-storage.ts`, behind the `ObjectStorage` port. Keys (names only; values come from the platform secret and configuration path, never the repository): `CORE_MEDIA_S3_ENDPOINT`, `CORE_MEDIA_S3_BUCKET`, `CORE_MEDIA_S3_REGION`, `CORE_MEDIA_S3_ADDRESSING_STYLE` (`path` or `virtual-host`), `CORE_MEDIA_S3_CONDITIONAL_CREATE` (`supported` or `unsupported`), `CORE_MEDIA_S3_ACCESS_KEY_ID`, `CORE_MEDIA_S3_SECRET_ACCESS_KEY`, and optional `CORE_MEDIA_S3_PART_SIZE_BYTES`, `CORE_MEDIA_S3_REQUEST_TIMEOUT_MS`. One further optional key sits beside them but is not part of the provider identity: `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS` (see the digest step guard below). The endpoint must be an `https` origin (`http` only on a loopback host). Configuration that fails to parse falls back to an object store that refuses every operation. Credentials are redacted values and appear in no error or log. The adapter has no retry, backoff or request timeout default; its request timeout applies only when configured. The digest step guard is the one default, and it is not the adapter's.

**The provider identity is derived from the endpoint origin and the bucket name.** Renaming the bucket, moving to another domain or restoring into another bucket changes it, and every asset recorded under the old identity then answers `UNAVAILABLE`; no re-pointing path exists, so plan such a change before it is made. Rotating credentials does not change it. The adapter writes at most 10,000 parts: an object larger than the part size times 10,000 cannot be written, reserve still accepts it, and its upload ends unavailable. No lifecycle rule for unfinished multipart uploads is configured or verified.

## Provider test matrix and the opt-in real-endpoint run

The S3 suites (`core-media-s3-storage`, `core-media-recovery-s3`, the S3 half of `core-media-upload-edge`) are registered once per **provider row** (`tests/support/s3-provider-under-test.ts`), so the same assertions run against every row and a result names its row. Rows: the MinIO emulator (only when `CORE_MEDIA_S3_*` names a loopback server; skipped otherwise), and three rows of the **R2-behaviour mock** (`tests/support/r2-behaviour-mock.ts`: path style, virtual-hosted, and with the documented limit of one write per second per key switched on). **The mock is built from Cloudflare's public documentation and is not R2**: it encodes only statements the documentation makes (region `auto`, SigV4 validation, create-only `412`, no object versioning, `411` without a length, the 404 error shapes, multipart ETags and part rules, the documented limits) and answers `501 ... NOT VERIFIED` to anything the documentation does not state. Every source URL and every behaviour left unencoded is listed in the header of that file; no row of it is evidence about R2.

One command runs all rows: `mise exec -- pnpm --filter @app/core-runtime test:s3-provider`. A further **REMOTE** row exists only with `CORE_MEDIA_S3_ALLOW_REMOTE=1` and `CORE_MEDIA_S3_*` naming a real endpoint: it is refused unless the bucket name contains the safety marker (`-d20-test`, or `CORE_MEDIA_S3_TEST_BUCKET_MARKER`, at least five characters), it records every key it creates and removes exactly those keys (and the unfinished uploads under them) at the end; it reads only the bucket's list of unfinished uploads to find them and deletes nothing else. The tests that inject faults through the local proxy (plain HTTP, loopback only) are skipped on this row. It writes to the bucket: use a throwaway bucket created for it. Without the flag a non-loopback endpoint is refused exactly as before. No runbook is checked in, and the remote row has not been run.

The command does not include `core-media-upload-edge` (it needs PostgreSQL) or the Shell end-to-end suites (they also need SpiceDB); both ran against the mock rows too: the first registers the same rows, the second can use the mock as its S3 upstream through `tests/support/r2-behaviour-mock-server.ts`, which starts the mock as its own process and writes `CORE_MEDIA_S3_*` to a file. The version pin of an unversioned provider (`etag:<ETag>`, see the integrity section) is proven against a provider that sends no version id in `core-media-r2-mock-version-pin`. A virtual-hosted configuration whose endpoint is an IP address is refused at configuration time, because a bucket cannot be a subdomain of an address.

## The required CI run and its evidence record

CI runs the Shell end-to-end suites (`core-media-e2e-*`), the three S3 provider suites and the real Catalog chain (`scripts/integration/core-media-catalog-handoff.test.mts`) in one owner-integration task, `whole:core-media` (`scripts/ci/run-core-media-proof.sh`), against a MinIO emulator started from the image `docker-compose.yml` pins (**not R2**); the ordinary Shell, Core-runtime and root shards leave those files out. The task runs when the Shell, Core runtime or Catalog is affected. The task sets `D20_E2E_REQUIRED=1`, so a scenario or provider row it cannot execute fails instead of skipping, and runs `core-media-e2e-digest-step-guard` on its own with `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS=50`. Without the switch a local run skips what it is not configured for, as before.

The job uploads `core-media-evidence-<attempt>` (`core-media-evidence.json`), generated by `scripts/ci/core-media-evidence.mts` from that run's own test reports: commit, run id and URL, each run's non-secret settings and their fingerprint, and per file the passed, failed and skipped counts with every case name and result. A declared file that failed is `FAIL`, one with a skipped or unreported case is `NOT VERIFIED`, and either fails the job. It records test results only: the byte sizes, digests and permission outcomes of #1446 are asserted inside the cases, not copied into the record, and it changes nothing about what the Catalog chain leaves unrun ("Known gaps").

## Measured limits (facts, not product caps)

No product size limit, MIME allowlist or retry policy is defined by Core Media. Facts and their sources:

| Fact                            | Value                                                                                                                  | Source                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| S3 multipart structure          | minimum part 5 MiB, at most 10,000 parts, all parts but the last equal                                                 | S3 protocol; `s3-config.ts`, `s3-object-storage.ts`                |
| Request body without length     | refused (`411`) by the edge; a stream body without length is not accepted by node `fetch` or workerd against MinIO     | measured 2026-11-20 against the emulator (probe and workerd spike) |
| Adapter memory (node, emulator) | peak growth about 114 MiB for 64 MiB and for 1 GiB objects (bounded, not proportional)                                 | measured 2026-11-20, MinIO emulator                                |
| Native digest on workerd        | 64 MiB hashed in 289 ms wall; a JavaScript hash needs about 1.4 s for the same bytes                                   | measured 2026-11-20, local workerd                                 |
| Worker CPU class (Shell)        | 200 ms; not measurable on local workerd                                                                                | NOT VERIFIED                                                       |
| Digest step guard               | 5 seconds per digest step (one chunk write or the final close), not per object; a technical guard, not a product limit | `media/content-digest.ts`; `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS`     |
| Cloudflare R2 limits            | documented upstream (for example 1 write per second per key, multipart rules)                                          | provider documentation only; no R2 run                             |

**The digest step guard is not a maximum object size.** `DigestStepTimeout` (default 5 s, a `Context.Reference` read at the moment of each step) wraps exactly two platform calls of `ContentDigest`: `add`, one `writer.write` of one chunk, and `finish`, the `close` plus the digest read. It never spans the object: the unit test `core-media-content-digest` drives six steps of 30 ms under a 100 ms guard and none is stopped, and a step that never answers fails as unavailable at the guard. Setting it needs `CORE_MEDIA_DIGEST_STEP_TIMEOUT_MS` (a positive integer of milliseconds) provided through `mediaDigestStepTimeoutLayer`; unset keeps 5 s. The Shell provides it beside the object store (`coreMediaObjectStorageLive`), so the download, the byte PUT and the generated confirm route read it; a malformed value does not stop the host: it logs `core.media.digest-step-timeout.invalid` with the failure reason and the built-in 5 s applies. A step that exceeds the guard is unavailable, never proven corruption: the byte PUT and the confirm answer a retryable 503 problem, a download whose first chunk is still waiting for its digest step closes without a complete body, and the asset stays as it was (`uploaded` or `ready`, never `failed`), so the same request succeeds once the platform answers in time (Shell E2E `core-media-e2e-digest-step-guard`, a stand-in `crypto.DigestStream` on Node, emulator, NOT R2). The same code also runs on a local workerd: `scripts/tests/core-media-verified-read-workerd.test.mts` bundles the real `verified-read.ts` and `content-digest.ts` into a Miniflare Worker (run alone with `mise exec -- pnpm exec rstest --project scripts scripts/tests/core-media-verified-read-workerd.test.mts` from `app/`, no container) and shows the native `DigestStream` verifying an 8 MiB multi-chunk object, a same-length swap as `integrity_failed`, an early clean end and an aborted stream as `unavailable`, and a step delayed (a delay wrapped around the real native stream) past a configured guard as unavailable (`digest_unanswered`) while the built-in 5 s lets the same step pass. That is a local workerd, not a deployed Worker, and a delay is not a hung platform call. `openVerifiedMediaStream` carries the guard of its request into the returned body, because the transport runs that body in its own context. For scale only: at the measured 64 MiB in 289 ms (about 221 MiB/s) one step would have to carry roughly 1.1 GiB to need 5 s, and the chunks a transfer hands to the digest are the transport's, not the object's. What is **not** measured and so not claimed: the longest `close` after a very large object on a deployed Worker, any object above the 1 GiB node memory run, and whether `close` waits for queued hashing proportional to the queue. If a product maximum object size is wanted it must be decided by its owner from a measurement on the real Worker and the real provider (the largest object that completes reserve, stream, confirm and a verified download within the deployed CPU and ingress limits); this page proposes no number.

## Recorded decisions

Approved by the person directing the D20 implementation, in its sessions of 2026-11-19 to 2026-11-23: the reserve, stream, confirm upload; the byte `PUT` edge with its accepted risk; the redemption table; naming `catalog` in the Current read's allow-list; download verification while streaming, with a different size recorded as `failed`; the `ingestionSource` consistency check; the 5 s digest step default; an administrator-made enrollment of the integrity principal, local setup using the same Action; one change set including the system-workload enrollment; leaving the real provider run and the adoption by existing environments to follow-ups.

Approved by the same person on 2026-11-26:

- The client declares size and SHA-256 at reserve, and the id is returned while the asset is still `uploaded`.
- Current stays narrowed by the company the requester selected: another company's asset answers `ABSENT`, as metadata and download treat it.
- A size the object store can never write is refused at reserve.
- A Catalog assignment that Core answers nothing for keeps the whole Catalog read at `503`; the public response gains no `OWNER_CHECK_REQUIRED` value.
- Upload keeps two capabilities; a byte `PUT` past `uploaded` is decided under the confirm capability; an unanswered digest step is a retryable `503`; no cleanup code ships without a caller; CI runs the Core Media suites against an emulator and fails on a skip.
- The deviation from #1443 recorded below ("The Catalog port of #1443").

## Known gaps

- **No run against Cloudflare R2 or Wasabi.** Credentials were not supplied; every provider behaviour was executed only against the MinIO S3-compatible emulator, which is never evidence for R2.
- **A tenant without an enrolled `core.media.integrity` principal records nothing, and nothing enrols it automatically.** A tenant administrator enrols it with `core.identity.change-system-workload-enrollment` (module `core.media`, workload `core.media.integrity`; see "Enrolling the integrity principal"), but neither the stage accounts file nor the local seed does it (locally it is the separate `pnpm local:enrol-integrity` step), so a tenant nobody enrolled still aborts a proven-corrupt download, leaves the row `ready` and logs `core.media.integrity.unrecorded`. A row confirmed without a provider pin is compared on size only, so a same-length substitution that nobody downloaded stays `AVAILABLE` for it (see the integrity section).
- **What the real Catalog chain covers.** `scripts/integration/core-media-catalog-handoff.test.mts` runs a compiled Catalog server, the production Shell (delegated gateway route, hosted `asset-current` receiver, upload routes), PostgreSQL, SpiceDB and the object store (emulator, NOT R2), with Product and Variant assignments written by Catalog's own Actions: `AVAILABLE`, `CURRENT_UNVERIFIED` (reserved, not stored) and `ABSENT` (never issued), the change to `AVAILABLE` once Core stores the bytes, a new upload changing no assignment, and an explicit remove-and-assign replacement that keeps the old assignment in Catalog's history and the old asset in Core. It runs in CI inside `whole:core-media`; locally it needs `CORE_MEDIA_S3_*`, built Catalog, Market Catalog and Shell artifacts from a clean commit (with `ULTRAMODERN_SOURCE_REVISION` naming it) and the integration services, and skips without a store. The requester's identity, grants and credentials are seeded fixtures, not a real sign-in journey. The other owner states are covered by `core-media-e2e-catalog-handoff` (a consumer read that declares Catalog's call, in one process) and by Catalog's unit tests of its adapter; a company selection, a refused capability, an outage and a damaged object were not run through the Catalog server itself.
- **Existing environments do not receive the capabilities** because the published authorization release is pinned and no code publishes a later one; a fresh database does. This is out of scope for D20; the follow-up is not filed.
- **`scanning` has no producer.** The state is accepted and never presented as usable, but nothing moves an asset into it.
- **The client routes have no UI.** Reserve, confirm and rename are HTTP routes and a typed client operation (`executeUploadAsset`, `executeConfirmAsset`, `executeRenameDisplayFilename` in `src/api/auth-client.ts`); no page calls them (UI is out of scope).
- **Other owners (UNVERIFIED, nothing here is claimed as checked):** production Privacy and retention assessment and physical deletion belong to their owners. Provider-side backup or replication (Wasabi is the probable backup target) needs a named operations owner; a backup copy extends retention beyond the primary object; and the Privacy owner must define, before production, what erasure means for the primary object and for every backup copy. None of this was configured, run or verified in D20.
