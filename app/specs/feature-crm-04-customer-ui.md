# Feature: CRM 04 Customer UI

## Feature Description

Implement ticket 4, "Implement the Customer UI," from `app/tickets.md`. Adapt the generated private
Customers page into a paginated company list and direct-detail workspace with create, edit, and
soft-delete flows. Consume only the completed generated Customer Effect clients and represent every
typed route/mutation state without adding CRM search controls or behavior.

## User Story

As an authorized CRM user
I want to browse and maintain company Customers
So that the shared tenant directory remains accurate and safe to use

## Problem Statement

The Customer backend is callable but has no usable presentation. The UI must preserve Action/read
typed errors, separate deletion from editing, keep shareable list/detail state in the URL, work on
narrow screens, and localize all visible/accessibility copy.

## Solution Statement

Use the page generated by ticket 2 and the Customer directory/Action clients completed by ticket 3.
Compose existing `@techsio/ui-kit` Table, form, Dialog, Button, StatusText, and Toast components.
Use Figma file `GWzuNz24M0GzeOgGtuylj1`, page `Pre-Alpha Repo`, only to understand general list,
detail, form, dialog, and interaction placement. Do not use Figma for business requirements,
styling, colors, spacing, branding, or any page named `Pre-Alpha`.

## Implementation Plan

### Phase 1: Foundation

Inspect only Figma `Pre-Alpha Repo` for structural patterns, then define serializable route state,
view models, URL parameters, localized copy, and exhaustive typed error-to-UI mapping.

### Phase 2: Core Implementation

Build the semantic list/detail workspace and create/edit/delete dialogs with existing UI kit

recoverable conflicts, and test route, accessibility, responsive, localization, and typed states.

## Testing Strategy

### Unit Tests

Test view-model/error mapping, URL codecs, form validation, component states, destructive dialog
focus/keyboard behavior, translations, and explicit absence of search controls.

### Integration Tests

Route tests mock only the generated Effect clients to prove loader/mutation composition,
invalidation/refetch, conflict recovery, typed transport/decode failures, and URL-backed state.

### Edge Cases

- The selected Customer is deleted or unavailable after the list loaded.
- A stale edit/delete collides with another user.
- Optional structured address is partially supplied.
- Company name and address are very long on a narrow viewport.
- Module is read-only/deprecated and must remain readable but non-writable.
