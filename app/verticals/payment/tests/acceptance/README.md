### What is not proven

- **Provider sandbox (L4) is NOT RUN (credentials absent)** for all three gateways (N13). Live response shapes,
  provider idempotency, the Stripe default API version and the Comgate DELETE cancel path (ORIGIN C-11) are proven
  only against documented bodies. GoPay v4 (create, lookup, DELETE cancel, refund resource) has no sandbox run yet;
  that run plus GoPay's written confirmation is the D-P1 merge gate.
- **Comgate refund completion** is read only from the production settlement statement (D-P2). Sandbox payments have
  no statement, so a sandbox refund stays REFUND_PENDING. The live row shape (refund rows in `singleTransfer`, `ID od
klienta` = our refId, `Merchant`) is unverified until one small real production refund (N10).
- **Relay end to end.** The Payment relay is mounted on the real Modern server (`/api/payment/v1`, all deployment
  profiles), and that run proved its refusals and transport headers: no-store, problem content type, no API key
  challenge, no locale redirect, batch alias and OpenAPI refused, nothing under the Shell mount. A successful
  capture through the real Shell, the Core gate and the Payment release in one test did not run. Its halves ran:
  the Shell relay with the real handlers at unit level, the route Read and capture under a verified route scope
  natively in Payment, and Shell route-scope issuance at unit level. The Comgate acknowledgement content type
  (`application/x-www-form-urlencoded`) is asserted only by the Shell unit test, whose environment drops headers.
- **Driver end to end.** The reconciliation driver ran natively against the in-process A10 runtime; its calls to the
  Shell relay are proven with recorded relay answers (unit). The real Shell -> Core A10 hop under a Payment route
  scope with real 409/403 bodies did not run in one test. `/ready` of the Payment worker does not cover the driver
  loop.
- No real PSP delivery reached a deployed endpoint; that needs a stage deploy. PSP IP allow-lists and stage edge
  reachability are unverified.
- The capture Action under Module States ran only against the Core gate in unit tests. The native Module State
  matrix lists the 16 C16 entrypoints and does not include `capture-provider-notification`.
- Outbox claim eligibility per Module State, claim leases and backoff are Core runtime behaviour, proven in the Core
  Outbox suite with a generic consumer, not with the Payment workers.
- No C16 cross-owner journey (Storefront, Checkout, Order, Billing) and no production readiness are claimed.

### Conformance blockers returned to PO

These are explicit scope decisions for the #1159 completion gate. No gateway is silently dropped. Comgate collect
is no longer blocked: the collection caller supplies the payer contact (D-P3), and Comgate enablement needs the
same source authorities as every family.

- **N2** Governed apply path: A10 admits the `payment.provider-reconciliation` workload, and the driver marks an
  ACKNOWLEDGED operation `OUTCOME_OVERDUE` (then INDETERMINATE) after its round budget. PO confirms that meaning.
- **N8** GoPay cancel runs on Payments API v4 (`DELETE /payments/{id}` plus lookup). It merges only after a v4
  sandbox run and GoPay's written confirmation that the production merchant can use v4. If either fails, GoPay
  cancel goes back to CANCEL_NOT_EFFECTED and PO decides whether A6 rejects GoPay cancel.
- **N10** Comgate refund completion needs one small real production refund to confirm the statement row shape. A
  refund rejected after `code 0`, or a payer-bank rejection after the statement row, has no machine source.
- **N14** CANCEL_CONFIRMED means "the provider states this payment can no longer be paid" for all three families,
  and stays correctable by later contrary evidence. PO confirms it once.
- **N15** Settlement and remittance are not mapped for any provider. Settlement deliveries are stored as ignored and
  create no Payment operation.
- **Privacy** Payment holds the payer contact transiently (deleted at prepare, purged after 48 h) and sends it to
  Comgate and GoPay. The privacy declaration of Payment as transient processor, the providers as recipients and the
  frozen propose-mode commands that keep the contact are open.

### Adoption gaps settled at fixture level

`src/integrations/paykit-adoption/ORIGIN.md` records C-7 and C-11 as settled at fixture level:

- C-7 (form-encoded Comgate body): the push decoder picks JSON or urlencoded by content type. `comgate-push` decodes
  the documented urlencoded push, and the L2 matrix verifies the JSON push through the adapter. The REST v2 status
  read is JSON. A form-encoded live answer is unverified until L4.
- C-11 (two cancel paths): the L2 matrix asserts that a Comgate cancel sends exactly the transaction-id `DELETE` and
  then the confirming status lookup. Whether that path behaves as documented is unverified until L4.

### Dependencies recorded in the baseline run

- **Owner ports fail closed in production.** `api/payment-production-layers.ts` wires every downstream owner
  port (C15 term + CCC entitlement, C17 gateway binding, Delivery COD capability, pickup capability, #331
  commitment outcome, refundable items) to its unavailable layer. In production every branch that needs one
  of them answers `UNAVAILABLE_TO_VERIFY` or refuses; the owner behavior above is proven only through the
  public-contract fixtures in `tests/support/*`.
- **Permission is a scripted gate.** Every Action and Read test decides Principal Permission with the scripted
  Core test gate (`allowed` / `denied`), not with SpiceDB or the native permission harness.
- **C17 #1159 provider conformance was outstanding at the C16 baseline.** The C17 section above now traces it;
  provider sandbox evidence is still NOT RUN. Every gateway result above (collection, gateway refund,
  recovery, provider idempotency, account isolation) proves only how Payment handles the declared C17 adapter
  contract, through a fixture. It does not prove GoPay, Stripe or Comgate behavior, provider idempotency
  support or production readiness.
- Composition phase, expiry and fence are varied only in acceptance-composition-fence; every other suite uses the
  Core composition fixture. Phases there are set by the clone's admin connection, except the drain scenario,
  which uses Core's close-admission, drain, seal and Outbox matcher.
- An INDETERMINATE Payment Operation (unknown monetary effect) is Core durable work of `payment.core` under the
  revision of the invocation that made it unknown (custom migration `enforce-payment-ledgers`). While
  it exists Core refuses to drain or seal that release; a proven outcome or governed decision clears it. Every
  effect-capable dispatch is completion-bound (#1158): the `payment.core.operation-requested.v1` row of a gateway
  COLLECT, CANCEL_OR_VOID or REFUND, and every lookup or replay `payment.core.operation-recovery-requested.v1` row,
  is Core durable work of the admitting revision until Payment's registered worker completes its delivery, so R1
  neither drains nor seals while a gateway dispatch is unfinished. Business waiting (PENDING) and the request of a
  non-gateway binding (bank, COD, pickup) are not tracked. Integration tests that admit tracked work publish the
  matching revision with Payment's real registered subscriptions through `installPaymentTestCompositionAuthority`
  (`tests/integration/composition-authority-fixture.ts`), which holds the authority lock Core's native suites
  share; isolated clones publish the same registration.
- Downstream owners (Storefront, Cart, Delivery, Order, Commitment #331, Fulfillment, Billing, bank/ERP/POS/
  carrier transports) are represented only by named public-contract fixtures. No production journey exists.
