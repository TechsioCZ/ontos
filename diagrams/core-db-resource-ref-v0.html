OntOS V0 Core Process And Database Boundary

Start here when designing any V0/V1 ERP feature. First classify the process, then pick the owning runtime path, then use the schema rules below. Core does not have a central entities or relations registry. When Core needs to point to a business object, it stores a value-style ResourceRef: tenant_id + module_key + resource_type + resource_id.

Core schema property.registry module billing.core module
Foreign keys only inside ownership

Modules use physical foreign keys for their own tables and stable Core boundaries such as tenant, legal entity, and principal.

Cross-module references are values

Modules do not create foreign keys to other modules. They store ResourceRefs, and the owning module resolves details through a resolver or read model.

Projections are not the source of truth

Search indexes, audit targets, media links, and outbox subjects may point to ResourceRefs, but business truth stays inside the owning module.

Start Here: Guideline For Any New Process

1. Classify the user intent
Decide whether it is UI-only, read/list/report/export preview, Core/system write, single-module write, or cross-module workflow.
2. Pick exactly one owner
Core owns platform concerns. A module owns its business facts. Cross-module workflows still have one command owner and reference others through public APIs and ResourceRefs.
3. Use the Core envelope for every write
All durable writes pass through principal, tenant, legal entity, module state, authorization, policy, validation, idempotency, audit, event, and outbox handling.
4. Keep reads lighter than writes
Reads do not create action invocations. They still resolve tenant/principal/module state/authz and create data-access evidence only when policy requires it.
5. Never add cross-module foreign keys
Inside one owner, use normal foreign keys. Across modules, store ResourceRef values and resolve details through the owning module contract or a projection.
6. Treat imports as controlled writes
Upload and staging can be separate, but accepted imported rows must end as target module actions or validated import handlers with protocol and evidence.
7. Let modules own specialized infrastructure
A module may use R2/S3, graph stores, vector stores, queues, or external APIs when its domain needs them. It declares the capability and accesses it through Core SDK/platform contracts.

Platform SDK Rule: Modules Can Add Their Own Infrastructure

Default rule
Core is not modified for every module-specific database, bucket, model, graph, queue, or external API. The module owns its specialized infrastructure behind its public contract.
What Core enforces
Core exposes SDK/library functions for tenant context, authz, module state, action invocation, idempotency, audit, evidence, ResourceRef, outbox, secrets, config, and worker claims.
What the module owns
The module owns its domain tables, adapters, migrations, private stores, indexing strategy, worker logic, and public API. Other modules cannot reach into those internals.
When Core changes
Change Core only when the need is shared platform capability, tenant-wide policy enforcement, common evidence/audit semantics, provisioning, billing, security, or operational control.
Large files example
A module can use R2/S3 for large files. Core SDK supplies tenant-scoped config, secrets, signed access helpers, media/evidence metadata hooks, audit hooks, and retention policy checks.
Graph/vector example
A module can use Neo4j, pgvector, Qdrant, or another store if it owns the use-case. Core only sees declared capability, health, evidence/audit metadata, and ResourceRefs when exposed.

Capability Control Plane: How Core Knows About Module-Owned Infrastructure

Decision sentence
Core owns the control plane for module capabilities; the module owns the data plane for its specialized infrastructure.
1. Module declares capability
The module manifest declares capability keys such as blob.large_files, vector.search, graph.relationships, or integration.booking_channel, including policy, evidence, health, and event expectations.
2. Core binds it per tenant
Core records whether the capability is enabled for a tenant/legal entity, which provider/config profile is used, which secret reference applies, and which data classification/retention policy is required.
3. Runtime gives the module an SDK handle
The handler does not receive raw global credentials. It receives a tenant-scoped SDK capability handle that already knows action invocation, principal, tenant, policy, audit, evidence, trace, and outbox context.
4. SDK logs governed operations
For sensitive or durable operations, the SDK writes operation metadata: capability key, provider, operation kind, status, duration, target ResourceRef, external object reference hash, bytes/counts when relevant, and error code.
5. Module keeps implementation details private
Core does not know raw vector contents, graph schema, provider-specific tables, external API payloads, or private indexes unless the module deliberately exposes metadata, evidence, or a public read model.
6. Health and operations are reported upward
Module workers report capability health, lag, failed jobs, provider errors, rate limits, and replay status through Core health/telemetry hooks so operations can see tenant impact without owning the provider client.

5. Compact Rules For Reads, Reports, Exports, And Imports

Detail/list/search/report read
Resolve principal, tenant, legal entity, module state, read authorization, and policy. Serve from the owning module endpoint, reporting endpoint, Postgres view, or projection. No action invocation is created.
Data access evidence
Create CORE_DATA_ACCESS_EVENTS only when the operation is sensitive, exported, downloaded, audited by contract, or required by tenant policy.
Export preview
Same as read. It becomes a durable write only when an export file/job/protocol is created, because that creates an artifact and evidence trail.
Import upload and staging
Store source files as media/evidence, create an import run, parse into staging, validate row-level errors, and keep an import protocol from the beginning.
Accepted imported rows
Accepted rows must call target module actions or validated import handlers. The target module still owns its canonical tables, audit, domain events, and ResourceRefs.
Background work
Workers claim outbox/import jobs after the transaction. They update projections, files, protocols, notifications, and integrations without becoming the source of truth.

Module Key Role Names

producer_module_key
Write-side module that emitted a domain event or owns an outbox message contract. It answers "who produced this fact/message?"
serving_module_key
Read-side module that served a read/list/search/export/download surface. It is the read equivalent of producer, but the operation did not create a domain fact.
subject_* ResourceRef
The primary resource a domain event or evidence artifact is about. For events this is the business subject of the fact.
target_* ResourceRef
The resource an action, audit checkpoint, data access event, or media link was aimed at. For list/report/export it can be null because the operation may cover many resources.
source_* ResourceRef
Provenance of derived data, such as a search document or invoice line source. It answers "where did this derived row come from?"

CORE_TENANT_MODULE_STATE_CHANGES: Actor Semantics

changed_by_principal_id
Effective actor of the change. For a normal admin this is the admin. For support impersonation this is the impersonated principal, because that principal is the runtime subject of the change.
action_invocation_id
Source of truth for auth context. For change_source=user and support, it should be required; it lets us trace auth_method, auth_context_ref, and any impersonated_by_principal_id.
Why no local impersonation column
Do not duplicate impersonated_by_principal_id into every derived or history table. The action/audit envelope already records who actually held the session or support permission.

CORE_ACTION_INVOCATIONS: Meaning Of Runtime Fields

auth_method
Runtime authentication path: session, api_key, system, or support_impersonation. This is not authorization; SpiceDB and policy handle authorization.
auth_context_ref
Non-secret runtime reference for context lookup, such as a session id, BetterAuth API key id, support session id, or worker run id. Never store a raw token or API key.
trace_id / correlation_id
Reference to the Effect/OpenTelemetry trace and application correlation across frontend, API, database, and workers. The database remains the audit source of truth; tracing handles technical observability.
idempotency_key
Optional retry key from the client or integration. Same key plus same request returns the original result; same key plus different request is a conflict.
status
received, rejected, running, succeeded, failed, replayed. This is the action-envelope lifecycle, not the business status of an invoice or reservation.
request_hash
SHA-256 hash of the canonical request envelope: action, tenant/legal entity, target ResourceRef, schema version, and normalized body. Used for idempotency and tamper evidence.
Action payloads
The baseline Core database does not store generic action request/response payloads. Exact or large evidence belongs outside the database in storage/archive only when an explicit evidence policy requires it; the database keeps the audit skeleton and optional reference.
CORE_DATA_ACCESS_EVENTS
Evidence for read/list/search/export/download: who accessed data, through which module, query hash, result count, result fingerprint, or stored artifact. It does not mean storing every response body forever.

CORE_EVIDENCE_REFERENCES: Evidence Registry

What lives in Postgres
Only evidence-registry metadata: tenant, source Core event, primary ResourceRef, evidence policy, media asset, retention, legal hold, classification, and status. No raw payload or binary content.
media_asset_id
Foreign key to CORE_MEDIA_ASSETS, where storage provider/key, optional version/generation, MIME type, byte size, and content_sha256 live. The evidence reference does not take ownership of the asset; it only says the asset is audit-relevant evidence.
artifact_content_sha256
Snapshot of the content hash at evidence-registration time. This pins the exact bytes even after storage migration, file rename, or presentation metadata changes.
Storage lock snapshot
storage_lock_scope, storage_lock_mode, storage_legal_hold, storage_retain_until, storage_lock_status, storage_lock_verified_at, and small storage_lock_evidence_json record whether the provider actually confirmed WORM/Object Lock. application_only means only our API is protected, not the storage provider.
source_kind + source FK
Discriminator plus exactly one physical foreign key: action, audit, data_access, or domain_event. Do not use a polymorphic source_id without a foreign key.
evidence_kind
Business evidence type: export, generated document, import file, signed document, compliance bundle, or action snapshot.
subject_* ResourceRef
Primary business object the evidence belongs to. Nullable because an export/report may include many ResourceRefs or only tenant-level evidence.
Retention fields
retention_policy_key, retain_until, legal_hold_until, and disposition_status control deletion, archive, and hold. Changes to these fields are auditable actions themselves.
data_classification
Asset-content classification for access control, exports, and retention: typically internal, confidential, or restricted.
No artifact redaction profile in V0
Redacted artifacts are not modeled as a baseline evidence flow yet. redaction_profile stays only on CORE_DATA_ACCESS_EVENTS for the redacted_payload mode.

CORE_AUDIT_EVENTS: Action Checkpoint Flow

sequenceDiagram
  participant Core as Core action runtime
  participant Authz as SpiceDB
  participant Policy as Policy layer
  participant Module as Module command handler
  participant Audit as CORE_AUDIT_EVENTS

  Core->>Audit: action.received / succeeded / system / action_received
  Core->>Audit: action.authn_resolved / succeeded / authn / principal_resolved
  Core->>Authz: Check permission
  Authz-->>Core: allowed or denied
  Core->>Audit: action.authz_checked / allowed|denied / authz / spicedb_permission_*
  alt authz denied
    Core->>Audit: action.rejected / denied / authz / spicedb_permission_denied
  else authz allowed
    Core->>Policy: Evaluate policy
    Policy-->>Core: allowed or denied
    Core->>Audit: action.policy_checked / allowed|denied / policy / policy_*
    alt policy denied
      Core->>Audit: action.rejected / denied / policy / policy_code
    else policy allowed
      Core->>Module: Validate and execute
      Core->>Audit: action.validation_checked / allowed|denied / validation / validation_*
      alt validation denied
        Core->>Audit: action.rejected / denied / validation / invalid_payload
      else execution succeeds
        Module-->>Core: committed canonical state
        Core->>Audit: action.executed / succeeded / execution / domain_outcome_code
      else execution fails
        Module-->>Core: failure
        Core->>Audit: action.failed / failed / execution / error_code
      end
    end
  end
outcome
allowed/denied are gate decisions. succeeded/failed are execution results or system-checkpoint results.
outcome_stage
Layer where the result was produced: system, authn, authz, policy, validation, or execution.
outcome_code
Stable machine-readable reason, for example spicedb_permission_denied, invoice_already_exported, validation_passed, or numbering_series_exhausted.
evidence_json
Small redacted supporting facts. It does not duplicate outcome and does not contain raw request/response data or full business objects.
Default audit profile
standard: received, authn_resolved, authz_checked, policy_checked, validation_checked, terminal event. sensitive adds extra checkpoints; minimal is only an explicit exception for noisy internal jobs.
Single source of truth
Do not use separate authz_decision/policy_decision columns. The result is always outcome + outcome_stage + outcome_code; facts live in evidence_json.

Data Access Evidence Policy

Who sets evidence_capture_mode
The frontend, API client, and handler do not set this ad hoc. Core runtime sets it from the declared endpoint/action descriptor.
metadata_only
Stores the access fact: actor, time, and target/query metadata. The result and result hash are intentionally not stored.
hash_only
Stores the query hash or result fingerprint. It is one-way: without a stored manifest, payload, or artifact, the content cannot be reconstructed from it.
redacted_payload
Stores a cleaned snapshot/summary in evidence_payload_json; redaction_profile is required only for this mode, otherwise it is null.
stored_artifact
The exact output is stored encrypted outside the database as CORE_MEDIA_ASSETS and audit-linked through CORE_EVIDENCE_REFERENCES. Typical examples are exports, PDFs, CSVs, and accounting packages.
System enforcement
Build/test requires an evidence policy for public read/list/search/export/download. The runtime wrapper applies it; database constraints guard local invariants, and stored artifacts require matching evidence references.
serving_module_key
Module that served the read/list/search/export/download operation. For example, reporting.basic may serve a report over billing/property data.
result_fingerprint_*
result_fingerprint_schema says how the hash was computed; result_fingerprint_hash is only a comparison fingerprint, not the result content.

Idempotency Contract From UI/API To Backend

sequenceDiagram
  participant UI as UI / API / MCP client
  participant API as Action endpoint
  participant Core as Core action runtime
  participant DB as Postgres
  participant Mod as Module command handler

  UI->>UI: Create stable idempotency_key for one user intent
  UI->>API: POST action + Idempotency-Key + payload
  API->>Core: Normalize request and compute request_hash
  Core->>DB: INSERT CORE_ACTION_INVOCATIONS with unique tenant/action/principal/key
  alt Insert succeeds
    Core->>DB: status = running
    Core->>Mod: Execute command handler
    Mod->>DB: Write canonical domain state
    Core->>DB: Store audit, domain event, outbox, trace correlation
    Core->>DB: status = succeeded
    Core-->>UI: Return result or stable resource reference
  else Unique key exists with same request_hash
    Core->>DB: Load original invocation
    alt original succeeded
      Core-->>UI: Return original result, mark replay if useful
    else original running
      Core-->>UI: 202 pending or short wait
    else original failed
      Core-->>UI: Return original failure or retry policy result
    end
  else Unique key exists with different request_hash
    Core-->>UI: 409 idempotency_conflict
  end
UI intent key
The frontend generates the key when the intent is created, for example when opening a create modal or initializing a form instance. Double-click, retry, or POST refresh must send the same key.
HTML form / refresh POST
A classic form has the key as a hidden input. After a successful POST, use POST/Redirect/GET so refresh repeats the GET detail, not the write request.
REST / MCP / integrations
For non-idempotent write actions, Idempotency-Key is required. The SDK or MCP adapter may generate it for one tool call; retry must reuse the same key.
External deterministic keys
Integrations should use deterministic keys, for example booking:reservation:123:create or bank-file:abc:row:42.
Backend is source of truth
Duplicate protection relies on an atomic insert and unique constraint, not on a disabled frontend button.
Business uniqueness
Idempotency handles repeated submission of the same intent. Real business duplicates still require domain uniqueness rules, such as normalized channel name or invoice number.

Write Flow And Ownership

flowchart LR
  request["UI / API / import invokes action"] --> authn["BetterAuth verifies session or API key"]
  authn --> binding["Core resolves CORE_PRINCIPAL_AUTH_BINDINGS"]
  binding --> ctx["Core resolves effective principal and tenant context"]
  ctx --> scope["Resolve ContextScope\nall / group / legal entity"]
  scope --> authz["SpiceDB permission check for scope and target"]
  authz --> moduleState["Core checks tenant-level module state"]
  moduleState --> moduleSetup["Module checks legal-entity setup if relevant"]
  moduleSetup --> modulePolicy["Owning module policy check"]
  modulePolicy --> command["Module command handler"]
  command --> moduleTables["Module writes canonical tables with local FKs"]
  command --> trace["Effect/OpenTelemetry trace\ntrace_id / correlation_id"]
  command --> audit["Core audit_events target ResourceRef"]
  command --> evidence["Core evidence_references\nretention / legal hold / media asset"]
  command --> events["Core domain_events subject ResourceRef"]
  events --> outbox["Core outbox_messages"]
  outbox --> search["Search worker updates optional core_search_index_entries"]
  outbox --> media["Media workers update core_media_assets processing state"]
