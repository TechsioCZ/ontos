OntOS V0 Core Database Boundary

Core nemá centrální entities ani relations registry. Když Core potřebuje ukázat na business objekt, uloží hodnotový ResourceRef: tenant_id + module_key + resource_type + resource_id.

Core schema property.registry module billing.core module
FK jen uvnitř vlastnictví

Moduly používají fyzické FK na vlastní tabulky a na stabilní Core boundaries jako tenant/legal entity/principal.

Cross-module odkazy jako hodnota

Mezi moduly se nevede FK. Ukládá se ResourceRef a detail řeší owning modul přes resolver/read model.

Projekce nejsou source of truth

Search index, audit targety, media links a outbox subjecty mohou ukazovat na ResourceRef, ale business pravda zůstává v modulu.

Module Key Role Names

producer_module_key
Write-side module that emitted a domain event or owns an outbox message contract. It answers “who produced this fact/message?”
serving_module_key
Read-side module that served a read/list/search/export/download surface. It is the read equivalent of producer, but the operation did not create a domain fact.
subject_* ResourceRef
The primary resource a domain event or evidence artifact is about. For events this is the business subject of the fact.
target_* ResourceRef
The resource an action, audit checkpoint, data access event, or media link was aimed at. For list/report/export it can be null because the operation may cover many resources.
source_* ResourceRef
Provenance of derived data, such as a search document or invoice line source. It answers “where did this derived row come from?”

CORE_TENANT_MODULE_STATE_CHANGES: Actor Semantics

changed_by_principal_id
Efektivní actor změny. U běžného admina je to admin. U support impersonation je to impersonovaný principal, protože ten je runtime subject změny.
action_invocation_id
Zdroj pravdy pro auth context. U change_source=user a support má být povinný; přes něj dohledáme auth_method, auth_context_ref a případné impersonated_by_principal_id.
Why no local impersonation column
Neduplikujeme impersonated_by_principal_id do každé derived/history tabulky. Kdo opravdu držel session nebo support oprávnění je součást action/audit obálky.

CORE_ACTION_INVOCATIONS: Meaning Of Runtime Fields

auth_method
Runtime cesta autentizace: session, api_key, system, nebo support_impersonation. Není to oprávnění; to řeší SpiceDB a policy.
auth_context_ref
Netajný runtime odkaz pro dohledání kontextu, např. session id, BetterAuth API key id, support session id nebo worker run id. Nikdy raw token/API key.
trace_id / correlation_id
Odkaz na Effect/OpenTelemetry stopu a aplikační korelaci napříč FE, API, DB a workery. DB zůstává auditní zdroj pravdy; tracing řeší technickou observability stopu.
idempotency_key
Volitelný retry klíč od klienta/integrace. Stejný klíč + stejný request vrací původní výsledek; stejný klíč + jiný request je konflikt.
status
received, rejected, running, succeeded, failed, replayed. Je to lifecycle obálky akce, ne business status invoice/reservation.
request_hash
SHA-256 kanonické request obálky: action, tenant/legal entity, target ResourceRef, schema verze a normalizované body. Slouží pro idempotency a tamper evidence.
Action payloads
Baseline Core DB neukládá generické request/response payloady akcí. Přesné nebo velké důkazy patří mimo DB do storage/archive jen podle explicitní evidence policy; v DB zůstane auditní kostra a případný odkaz.
CORE_DATA_ACCESS_EVENTS
Evidence read/list/search/export/download: kdo se díval, přes který modul, query hash, počet výsledků, fingerprint výsledku nebo stored artifact. Neznamená ukládat každý response body navždy.

CORE_EVIDENCE_REFERENCES: Evidence Registry

What lives in Postgres
Jen evidence registry metadata: tenant, zdrojový core event, primární ResourceRef, evidence policy, media asset, retence, legal hold, klasifikace a stav. Ne raw payload ani binární obsah.
media_asset_id
FK na CORE_MEDIA_ASSETS, kde je storage provider/key, MIME typ, byte size a hash. Evidence reference tím asset nepřebírá; jen říká, že asset je auditně významný důkaz.
source_kind + source FK
Discriminator a přesně jeden fyzický FK: action, audit, data_access, nebo domain_event. Nepoužíváme polymorfní source_id bez FK.
evidence_kind
Byznysový typ důkazu: export, vygenerovaný dokument, importní soubor, podepsaný dokument, compliance bundle nebo action snapshot.
subject_* ResourceRef
Primární business objekt, ke kterému důkaz patří. Je nullable, protože export/report může zahrnovat mnoho resource refs nebo jen tenant-level evidence.
Retention fields
retention_policy_key, retain_until, legal_hold_until a disposition_status řídí mazání, archivaci a hold. Změny těchto polí jsou samy auditovatelné akce.
data_classification
Klasifikace obsahu assetu pro řízení přístupu, exportů a retence: typicky internal, confidential, restricted.

CORE_AUDIT_EVENTS: Action Checkpoint Flow

sequenceDiagram
  participant Core as Core action runtime
  participant Authz as SpiceDB
  participant Policy as Policy layer
  participant Module as Module command handler
  participant Audit as CORE_AUDIT_EVENTS

  Core->>Audit: action.received / succeeded / system / action_received
  Core->>Audit: action.authn_resolved / succeeded / authn / principal_resolved
  Core->>Authz: Check permission
  Authz-->>Core: allowed or denied
  Core->>Audit: action.authz_checked / allowed|denied / authz / spicedb_permission_*
  alt authz denied
    Core->>Audit: action.rejected / denied / authz / spicedb_permission_denied
  else authz allowed
    Core->>Policy: Evaluate policy
    Policy-->>Core: allowed or denied
    Core->>Audit: action.policy_checked / allowed|denied / policy / policy_*
    alt policy denied
      Core->>Audit: action.rejected / denied / policy / policy_code
    else policy allowed
      Core->>Module: Validate and execute
      Core->>Audit: action.validation_checked / allowed|denied / validation / validation_*
      alt validation denied
        Core->>Audit: action.rejected / denied / validation / invalid_payload
      else execution succeeds
        Module-->>Core: committed canonical state
        Core->>Audit: action.executed / succeeded / execution / domain_outcome_code
      else execution fails
        Module-->>Core: failure
        Core->>Audit: action.failed / failed / execution / error_code
      end
    end
  end
outcome
allowed/denied jsou gate rozhodnutí. succeeded/failed jsou výsledky provedení nebo systémového checkpointu.
outcome_stage
Vrstva, kde výsledek vznikl: system, authn, authz, policy, validation, execution.
outcome_code
Stabilní strojový důvod, např. spicedb_permission_denied, invoice_already_exported, validation_passed, numbering_series_exhausted.
evidence_json
Malé redigované supporting facts. Neduplikuje outcome; neobsahuje raw request/response ani celé business objekty.
Default audit profile
standard: received, authn_resolved, authz_checked, policy_checked, validation_checked, terminal event. sensitive přidává extra checkpointy; minimal jen explicitní výjimka pro noisy interní joby.
Single source of truth
Nepoužíváme samostatné authz_decision/policy_decision. Výsledek je vždy outcome + outcome_stage + outcome_code, fakta jsou v evidence_json.

Data Access Evidence Policy

Who sets evidence_capture_mode
Nenastavuje ho FE, API klient ani handler ad hoc. Nastavuje ho Core runtime podle deklarovaného endpoint/action descriptoru.
metadata_only
Ukládá se fakt přístupu: actor, čas, target/query metadata. Výsledek ani hash výsledku se záměrně neukládá.
hash_only
Ukládá se hash dotazu nebo fingerprint výsledku. Je jednosměrný: bez uloženého manifestu/payloadu/artifactu z něj obsah nezrekonstruujeme.
redacted_payload
Ukládá se očištěný snapshot/summary do evidence_payload_json; redaction_profile je povinný jen pro tento mode, jinak je null.
stored_artifact
Přesný výstup je uložený šifrovaně mimo DB jako CORE_MEDIA_ASSETS a auditně svázaný přes CORE_EVIDENCE_REFERENCES. Typicky exporty, PDF, CSV, účetní balíčky.
System enforcement
Build/test vyžaduje evidence policy pro public read/list/search/export/download. Runtime wrapper ji aplikuje; DB constraints hlídají lokální invariants a stored artifact vyžaduje odpovídající evidence reference.
serving_module_key
Modul, který read/list/search/export/download obsloužil. Např. reporting.basic může servírovat report nad billing/property daty.
result_fingerprint_*
result_fingerprint_schema říká, jak byl hash spočítaný; result_fingerprint_hash je jen otisk pro porovnání, ne obsah výsledku.

Idempotency Contract From UI/API To Backend

sequenceDiagram
  participant UI as UI / API / MCP client
  participant API as Action endpoint
  participant Core as Core action runtime
  participant DB as Postgres
  participant Mod as Module command handler

  UI->>UI: Create stable idempotency_key for one user intent
  UI->>API: POST action + Idempotency-Key + payload
  API->>Core: Normalize request and compute request_hash
  Core->>DB: INSERT CORE_ACTION_INVOCATIONS with unique tenant/action/principal/key
  alt Insert succeeds
    Core->>DB: status = running
    Core->>Mod: Execute command handler
    Mod->>DB: Write canonical domain state
    Core->>DB: Store audit, domain event, outbox, trace correlation
    Core->>DB: status = succeeded
    Core-->>UI: Return result or stable resource reference
  else Unique key exists with same request_hash
    Core->>DB: Load original invocation
    alt original succeeded
      Core-->>UI: Return original result, mark replay if useful
    else original running
      Core-->>UI: 202 pending or short wait
    else original failed
      Core-->>UI: Return original failure or retry policy result
    end
  else Unique key exists with different request_hash
    Core-->>UI: 409 idempotency_conflict
  end
UI intent key
FE generuje key při vzniku intentu, například otevření create modalu nebo inicializaci form instance. Double-click, retry nebo POST refresh musí poslat stejný key.
HTML form / refresh POST
Klasický form má key jako hidden input. Po úspěšném POSTu použít POST/Redirect/GET, aby refresh opakoval GET detail, ne write request.
REST / MCP / integrations
U non-idempotent write actions je Idempotency-Key povinný. SDK nebo MCP adapter ho může generovat pro jeden tool call; retry musí použít stejný key.
External deterministic keys
Integrace by měly používat deterministické klíče, např. booking:reservation:123:create nebo bank-file:abc:row:42.
Backend is source of truth
Ochrana proti duplicitám stojí na atomickém insertu a unique constraintu, ne na disabled buttonu ve frontendu.
Business uniqueness
Idempotency řeší stejný intent opakovaně. Věcné duplicity musí pořád hlídat doménové unikáty, např. normalized channel name nebo invoice number.

Write Flow And Ownership

flowchart LR
  request["UI / API / import invokes action"] --> authn["BetterAuth verifies session or API key"]
  authn --> binding["Core resolves CORE_PRINCIPAL_AUTH_BINDINGS"]
  binding --> ctx["Core resolves effective principal and tenant context"]
  ctx --> scope["Resolve ContextScope\nall / group / legal entity"]
  scope --> authz["SpiceDB permission check for scope and target"]
  authz --> moduleState["Core checks tenant-level module state"]
  moduleState --> moduleSetup["Module checks legal-entity setup if relevant"]
  moduleSetup --> modulePolicy["Owning module policy check"]
  modulePolicy --> command["Module command handler"]
  command --> moduleTables["Module writes canonical tables with local FKs"]
  command --> trace["Effect/OpenTelemetry trace\ntrace_id / correlation_id"]
  command --> audit["Core audit_events target ResourceRef"]
  command --> evidence["Core evidence_references\nretention / legal hold / media asset"]
  command --> events["Core domain_events subject ResourceRef"]
  events --> outbox["Core outbox_messages"]
  outbox --> search["Search worker updates optional core_search_index_entries"]
  outbox --> media["Media workers update core_media_assets processing state"]

  moduleTables -. "No cross-module FK" .-> ref["ResourceRef value"]
